# 경계 계약 초안: 이슈 공장 ↔ dev-gate (2026-10-20)

두 세션이 따로 설계하는 것을 한 경계에서 맞추기 위한 초안이다. 이름은 아직 정하지 않았다(옛 delion 스킬을 대체할 쪽 = "이슈 공장").

## 합의된 전제 (이쪽 세션, Jin 확인)
- 개발 층의 진실의 원천 = GitHub Issues + Projects. Paperclip과 묶지 않는다.
- 브랜치 전략 기본값 = GitHub flow. 출시 주기가 있으면 태그만 추가.
- 구현 = Codex.
- 배포·외부 공개만 Jin 관문. main 머지는 dev-gate의 프로젝트별 검수 강도(빠르게/묶음/신중하게)를 따른다.
- 알림 = 프로젝트 오케스트레이터 하나가 그 프로젝트 창구로 (에디 아님).

## 맞춰야 할 것
1. **이슈 본문 형식.** 이슈 공장이 반드시 쓰고 dev-gate가 반드시 읽는 칸.
   - 목표 (한두 줄)
   - 범위 밖
   - **완료 확인 방법**: 실행 가능한 명령 또는 체크. dev-gate가 이것으로 ready 승격과 /goal 조건을 만든다.
   - 위험 경로 표시 (항상 사람이 보는 경로에 걸리는가)
   제안: 본문에 고정 머리글(`## Done when`) 또는 YAML 블록. 어느 쪽을 dev-gate가 파싱하기 쉬운가?
2. **의존성 표현.** GitHub 기본 기능(sub-issues, blocked-by)을 쓴다. 옛 delion-plan이 이미 이 방식이다.
3. **라벨 이름과 주인.** approved는 Jin만, ready·running·needs-jin은 dev-gate만 붙인다. 이슈 공장은 라벨을 만들기만 한다.
4. **`.dev-gate.yml`과 enroll.** 빈 폴더 셋업 단계가 저장소·칸반을 만든 뒤 `dev-gate enroll`을 부르는가, 아니면 셋업이 yml을 직접 쓰는가? 제안: 셋업은 enroll만 부른다(주인 하나).
5. **되먹임.** needs-jin과 아침 검수에서 나온 "이게 아닌데"가 다시 이슈 공장의 입력이 된다. 그 통로를 어느 쪽이 맡나?
