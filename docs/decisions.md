# 결정 기록

새 결정은 아래에 추가한다. 결정을 바꾸면 지우지 말고 "대체됨"을 표시하고 새 항목을 쓴다.

## 2026-10-20

### D1. 핵심 가치: 작업 사이를 자동화한다
- 결정: Foragent는 한 작업 안이 아니라 작업과 작업 사이(끝 → 검증 → 리뷰 → 다음 이슈 당기기)를 자동화한다.
- 이유: 한 작업을 끝까지 하는 것은 이제 순정 모델도 잘한다. 병목은 사람이 "다음 거"를 눌러 주는 것이다. oh-my-openagent, orwa-mahmoud/nightshift는 "한 작업 끝까지" 쪽이고, marcus/nightshift는 내장 잡일 처리 쪽이다.

- D1 보강 (2026-10-21, Jin): 모델이 아무리 좋아져도 서로 다른 성격의 일을 한 컨텍스트에 섞으면 성능을 다 내지 못한다 — (1) 이미 들어간 맥락의 잡음은 사라지지 않는다(공식 문서의 "kitchen sink session" 실패 패턴), (2) 일마다 완료 기준이 다르다, (3) 한 세션은 한 줄로 일한다(시간은 모델로 못 줄인다), (4) 하는 쪽과 판정하는 쪽은 나눠야 한다. 반대로 너무 잘게 쪼개면 넘김 손실과 레인 사이 틈(시험 6의 충돌)이 생기므로, 성격이 같은 일은 한 레인에 묶고 다른 일만 나눈다. "모델이 좋아지면 필요 없어지나?"에 대한 답이며 README 첫 줄 후보: "A smarter model still can't do unrelated work well in one muddled context. Foragent splits it by nature, runs it in parallel lanes, and checks each piece against its own bar."

### D2. 이름: Foragent
- 결정: Foragent. 명령은 `init` / `order` / `gate` / `morning`.
- 이유: forage + agent(스스로 다음 일을 찾아옴)와 for agent(에이전트를 위해 이슈를 찾아 넣어 줌) 두 뜻이 모두 제품 설명이 된다. 발음("포리전트")은 forage를, 글자는 agent를 강조한다.
- 확인: GitHub 같은 이름 22건, 최대 별 2개. npm·PyPI·Homebrew 비어 있음. GitHub 계정 `Foragent`와 foragent.com/.dev/.ai/.io 도메인은 이미 사용 중.
- 버린 후보: nightshift(같은 분야 저장소 존재), ForageNT(소문자로는 같은 이름이고 "NT"가 Windows NT처럼 읽힘), prowl 계열(큰 프로젝트 존재).

### D3. 두 층 구조
- 결정: 코드 변경으로 끝나는 일은 GitHub(Issues + Projects), 아닌 일은 Paperclip. Foragent는 GitHub 층만 다룬다. Paperclip과 묶지 않는다.
- 이유: Paperclip은 소프트웨어 개발에 특화되지 않았다. 묶으면 고장 지점만 는다.

### D4. 실행 루프는 gate(구 dev-gate)
- 결정: 반복문은 LLM 없는 스케줄러가 돌린다. 상태는 GitHub에만 둔다.
- 이유: 세션을 켜 둘 필요가 없고, 스케줄러가 죽어도 다시 켜면 이어 간다. Claude Code의 Workflow 도구로 만드는 안은 버렸다.

### D5. 기본값
- 브랜치: GitHub flow. 출시 주기가 있으면 태그만 추가한다.
- 구현: Codex. 실행기는 바꿀 수 있게 둔다.
- 관문: main 머지는 프로젝트별 검수 강도(빠르게/묶음/신중하게)를 따른다. 배포와 외부 공개만 사람이 승인한다.
- 알림: 프로젝트마다 오케스트레이터 하나가 그 프로젝트 창구로 보낸다.

### D6. 완료는 증거로 판정한다
- 결정: 이슈의 `## Done when` 코드 블록을 gate가 직접 실행한다. 모델의 "통과했다"는 믿지 않는다. 코드 블록이 없는 이슈는 실행하지 않는다.
- 상세: [contract.md](contract.md)

### D7. 승인은 그 시점의 본문에 대한 것이다
- 결정: 승인 뒤 이슈 본문이 바뀌면 승인은 무효다. 승인 뒤 달린 댓글은 세션에 넣지 않는다.
- 상세: [contract.md](contract.md) 추가 6

## 2026-10-20 (gate 쪽 추가)

### D8. 스케줄러는 프로젝트마다 하나
- 결정: gate 코드는 하나, 실행은 프로젝트마다 하나(launchd 작업 하나). 여러 프로젝트를 묶는 공용 슬롯은 v1에 넣지 않는다. 프로젝트당 동시 실행 1개 + `run_hours`로 시작한다.
- 이유: "프로젝트마다 사람에게 말하는 오케스트레이터는 하나" 원칙과 맞고, 한 프로젝트가 죽어도 다른 프로젝트는 돈다. 쿼터는 총량을 정할 뿐이라 공용 슬롯이 처리량을 늘리지 않는다. 맥미니 자원이나 쿼터 문제가 실제로 보이면 붙인다.
- 상세: [gate.md](gate.md) 8장

### D9. 판정에 LLM을 쓰지 않는다
- 결정: 상태 판정·승격·배정·예외 처리는 규칙으로 한다. LLM은 실행기 안과 적대적 리뷰에서만 쓴다. 실패 로그를 읽는 LLM 분류기는 선택 사항이다.
- 이유: 판정은 라벨과 시각만 보면 되는 일이다. LLM 판정은 할 일이 없어도 토큰을 쓰고 가끔 순서를 엉뚱하게 바꾼다.
- 상세: [gate.md](gate.md) 4장, 7장

### D10. 검수 강도는 되돌릴 수 있는 정도로 정한다
- 결정: `review`(fast/batch/careful)는 저장소 기본값 + 경로별 덮어쓰기. 검수 강도와 무관하게 `always_human` 경로, Done when이 참조하는 파일·테스트, `risk:high`, 배포·외부 공개는 사람에게 보낸다.
- 이유: 기준은 사용자 수가 아니라 되돌릴 수 있는가다. 같은 저장소 안에서도 실험 경로와 운영 경로의 위험이 다르다.
- 상세: [gate.md](gate.md) 6장

## 2026-10-20 (order 쪽 추가)

### D11. 최종 시험은 구현 전에 정하고 잠근다
- 결정: Done when의 최종 시험(인수 테스트나 실행 확인 명령)은 order 단계에서 구현 전에 쓰고 승인 PR에 함께 넣는다. 구현 PR이 그 파일을 건드리면 gate가 자동 머지를 멈추고 사람에게 보낸다. 작은 단위 테스트는 구현자가 쓴다. 미리 쓰기 어려운 이슈(UI 등)는 실행 결과만 확인하는 명령으로 대신한다.
- 이유: 구현자가 최종 시험까지 쓰면 문제를 푸는 대신 시험을 낮출 수 있다. 보장을 모델이 아니라 구조(시점 + 경로 잠금)에 두면 어떤 모델 조합에서도 성립한다.
- 상세: [order.md](order.md) O1

### D12. 모델은 단계마다 설정한다
- 결정: order에 쓸 모델과 gate 구현 모델을 각각 고를 수 있게 한다. 전역 기본값 + 프로젝트별 덮어쓰기. 설정 UI는 v1에서 `foragent config` 대화형 CLI로 한다.
- 이유: 사용자는 상황에 따라 모델을 바꾼다. 품질 보장은 구조에 있으므로 모델은 갈아 끼울 수 있어야 한다.

### D13. 아침 검수는 터미널 대화로 한다 (v1)
- 결정: `foragent morning`은 항목을 사람이 할 행동 순서(결정 → 재승인 → 검토 → 사람 확인 → 써 보기 → 참고)로 하나씩 객관식으로 묻고, 답을 GitHub에 남긴다. 창구에는 한 줄 알림만 보내고, 처리할 것이 0이면 보내지 않는다. 승인과 머지는 GitHub에서 사람 신원으로 한다.
- 이유: 가장 빠르고 만들 것이 적다. 결정·피드백은 입력이라 봇 신원으로 남겨도 되고, 사람 신원이 필요한 승인·머지만 GitHub에 둔다. 폰이 필요해지면 Slack 대화를 더한다.
- 상세: [morning.md](inspect.md)

### D14. 승인 신원: v1은 라벨, 공개 전에 사용자 전용 GitHub App (Q1 해소)
- 결정: v1(개인 사용·비공개 저장소)은 사람이 붙인 `approved` 라벨로 승인한다. 공개 전에는 에이전트가 사용자 전용 GitHub App(`foragent[bot]`)으로만 GitHub에 쓰게 바꾸고, 사람 계정 토큰을 에이전트 환경에서 뺀다. 승인은 사람이 머지한 승인 매니페스트 PR로 판정한다(contract 추가 7).
- 이유: 개인 비공개 저장소에서 현실적 위험은 에이전트 실수뿐이고, 결과는 되돌릴 수 있는 브랜치·PR이며, 위험 경로·시험 파일·배포는 gate가 따로 막는다. 공개 저장소에서는 외부인이 쓴 이슈 본문이 에이전트를 속여 스스로 승인하게 만들 수 있으므로 신원 분리가 필수다.
- 사용자 경험: 두 번째 GitHub 계정은 필요 없다. `foragent init`이 GitHub App manifest 흐름으로 앱을 만들고 설치한다(브라우저에서 클릭 두 번). 비밀 키는 사용자 컴퓨터에만 둔다. 우리가 앱 서버를 운영하는 방식은 쓰지 않는다.
- 남은 위험(v1): 맥미니 에이전트가 Jin의 관리자 토큰을 그대로 쓴다. Foragent와 별개로 이미 있는 위험이다.

### D15. 시간에 묶지 않는다, 검수 명령은 inspect, 짧은 이름은 fa
- 결정: gate는 승인된 이슈가 있으면 언제든 돈다. `run_hours`는 쿼터를 아끼고 싶을 때 쓰는 선택 설정이고 기본값은 항상. 문서의 "밤새/아침"은 "사람이 없는 동안/돌아와서"로 읽는다.
- 결정: `morning` → `inspect`(검수). review는 gate의 적대적 리뷰·검수 강도 설정과 겹쳐서 쓰지 않는다.
- 결정: 대화 단계 스킬 이름은 짧게 `fa-init` / `fa-order` / `fa-inspect`. 명령줄 프로그램은 `foragent`이고 `fa`를 별칭으로 둔다(`fa gate`, `fa config`). 확인: 맥미니에 `fa` 명령 없음, Homebrew에 없음. npm의 `fa`는 다른 패키지가 쓰고 있어서 npm 배포 이름은 `foragent`로 한다.

### D16. 검수는 목록이 아니라 "눈앞에 차려 놓기" (2026-10-20, Jin 첫 /fa-inspect 사용 후)
- 문제: 첫 실사용에서 Jin의 반응은 "그래서 내가 어디를 봐야 하는데?". 목록만 있고 어디를 보고·무엇을 만지고·무엇이 보이면 정상인지가 없었다.
- 결정: (1) 구현이 끝날 때 runner가 실행기에게 "사람이 1분 안에 확인하는 방법"(무엇이 바뀌었나 / 직접 해 보기 명령·URL / 정상일 때 보이는 것)을 `.foragent/TRY.md`로 쓰게 하고 PR 본문 "Try it" 절에 넣는다. (2) inspect는 그 확인 명령을 **미리 실행해 결과까지** 보여 준다(명령줄은 출력, 웹은 나중에 스크린샷·링크). (3) 결정 항목은 충돌하는 근거(이슈 문장, 시험 코드 줄)를 나란히 보여 준다. (4) 맨 위에 "결정 N건(약 M분) · 써 보기 K건(미리 확인함)" 한 줄.
- 이유: 사람이 찾아보는 수고를 없애는 것이 inspect의 존재 이유다. 미리 실행은 사람이 할 일을 대신 해 두는 것이고 결과를 보여 줄 뿐이다.

### D17. 언어 설정
- 결정: `language`(예: `ko`, `en`) 설정 하나. 전역 기본값 + 프로젝트 덮어쓰기. 기계가 읽는 형식(`## Goal`·`## Done when`·라벨·이유 코드·표식)은 항상 영어. 사람이 읽는 글(검수 화면, 알림, order 인터뷰, 실행기가 쓰는 QUESTION.md·TRY.md, needs-human 요약)은 설정 언어.
- 이유: 형식이 바뀌면 파싱이 깨지고, 사람이 읽는 글은 사용자 언어여야 한다. 공개 시 다른 사용자는 `en`.
- D16 보강 (Jin): 화면이 있는 기능은 직접 띄워서 보여 준다. TRY.md에 띄우는 명령·포트·열 주소·눌러 볼 순서·정상일 때 보이는 것을 쓴다. inspect는 머지된 코드를 임시 worktree에서 띄우고, 헤드리스 브라우저로 그 순서를 실행해 스크린샷을 모은 페이지를 열어 주며, Tailscale 주소(예: `http://mac-mini-1:3000/...`)를 함께 줘서 맥북·폰에서 바로 눌러 보게 한다. 검수가 끝나면 앱을 끈다. P7b는 명령줄 써 보기 + 웹용 TRY.md 형식·실행 틀까지, 실제 웹 검증은 프런트엔드 시험 저장소로 따로 한다.

### D18. Foragent는 순정 plan·goal을 대체하지 않고, 인터뷰를 여러 plan+goal로 쪼개 돌려준다 (2026-10-20, Jin)
- 결정: 한 작업 안의 반복(구현 → 확인 → 실패 피드백 → 재시도)은 실행기의 순정 `/goal`에 맡긴다(`claude -p "/goal <조건>"`은 비대화형으로 끝까지 돈다). 이슈 본문이 plan, `Done when`이 goal 조건이다. Foragent가 맡는 것은 순정 기능이 하지 않는 것뿐: 인터뷰를 plan+goal 단위로 쪼개기(order), 승인·순서·의존성·다음 일 당기기(gate), 독립 검증, 다른 모델 리뷰, PR·머지(runner), 사람에게 차려 보여 주기(inspect).
- 독립 검증은 유지: `/goal` 평가자는 명령을 실행하지 않고 대화만 보고 판단한다(공식 문서). runner는 goal이 끝난 뒤 Done when을 직접 다시 실행한다.
- Codex `/goal`은 실험 기능이다. 켜져 있으면 쓰고, 아니면 runner의 자체 재시도 루프를 예비로 쓴다.
- 이유: gate.md 1장 기준 "모델이 두 배 똑똑해지면 덜 필요해지는 장치는 넣지 않는다". 작업 안의 반복은 순정 기능이 좋아지면 저절로 좋아진다.

### D19. 핵심 가치는 "인터뷰만 하면 경험자의 준비를 대신 해 준다" (2026-10-20, Jin)
- 결정: Foragent의 차별점은 실행 루프가 아니라 인터뷰 → 쪼개기 → 셋업(order, init)이다. "라벨 붙은 백로그를 큐가 빌 때까지 처리" 같은 goal은 칸반·잘 쪼갠 이슈·완료 기준을 이미 갖춘 사람에게만 쓸모 있다. 바이브코더 대부분은 이 준비를 생각조차 하지 않는다. Foragent는 그 준비를 인터뷰 한 번으로 대신 한다. gate는 배관이다.
- 영향: order(P8)에 가장 공을 들인다. README 첫 문장도 이 가치로 고친다.

### D20. 순정 하네스 기능을 구조로 쓴다 (P7c 범위)

### D21. 레인: 의존성과 별개의 실행 단위 (2026-10-20, Jin — delion-wave에서 가져옴)
- 원칙(delion-wave): 의존성은 "언제 시작할 수 있나"를, 레인은 "충돌 영역과 이어서 하는 흐름"을 정한다. 둘을 같은 것으로 보지 않는다.
- 결정: 이슈마다 레인 하나(`lane:<name>` 라벨, 없으면 `lane:main`). 레인 안은 한 번에 하나(충돌 방지), 레인끼리는 병렬. 프로젝트당 동시 레인 상한 `max_parallel`(기본 2). D8의 "프로젝트당 동시 실행 1개"를 대체한다.
- order가 쪼갤 때 건드릴 영역을 기준으로 레인을 제안하고 승인 표에 보여 준다.
- 병렬 머지 위험: 머지 직전에 기준 브랜치가 검증 시점보다 앞서 있으면 최신 base를 합친 뒤 Done when을 다시 돌리고 통과할 때만 머지한다(충돌이면 시도 실패로 재시도).
- 순서: P7d(gate 레인·병렬) → P8(order가 레인 제안).

### D22. 레인 = 에이전트 = 영역 (2026-10-20, Jin)
- 결정: 레인 하나는 에이전트 정의 하나와 같다. `.foragent.yml`의 `lanes: {<name>: {paths: [...], agent: fa-<name>, executor?, model?}}` + `.claude/agents/fa-<name>.md`(얇게: 맡는 영역, 쓸 스킬, `memory: project`). 같은 정의가 세 일을 한다: 경로 = 충돌 영역(gate 병렬 판단, order 배정), 역할·스킬 = 구현 실행(`claude --agent fa-<name>`), 에이전트 기억 = 레인 안 이슈 사이의 학습 연속성.
- 효과: 세션은 이슈마다 새로(컨텍스트 깨끗), 배운 것은 레인 에이전트 기억으로 이어진다. 앞서 Jin이 원한 "역할별 기억"을 컨텍스트 오염 없이 얻는다.
- 선: 성격 묘사 금지(agency-agents 교훈). 정의는 영역·스킬·기억만, 실력은 스킬에.
- 실행기: claude는 `--agent`. codex는 정의 본문과 기억 파일을 읽어 지시문 앞에 붙인다(기억 쓰기는 claude 레인만).
- 만드는 쪽: `fa-init` 인터뷰가 첫 팀(레인)을 제안, `fa-order`가 이슈를 레인에 배정하고 새 레인이 필요하면 제안 → 사람 승인.
- 순서: P7d(gate가 레인 정의를 읽고 병렬 실행) → P8(init·order가 레인을 만들고 배정).

### D23. 스킬 라이브러리에서 골라 레인에 장착 (2026-10-20, Jin)
- 결정: `fa-init`이 인터뷰 결과로 팀(레인)을 제안할 때, 스킬 라이브러리에서 필요한 스킬만 골라 각 레인 에이전트에 장착한다. 첫 라이브러리는 `anthropics/knowledge-work-plugins`(Apache-2.0): engineering(system-design, testing-strategy, architecture, debug, …), design(accessibility-review, ux-copy, design-critique, …), data(sql-queries, validate-data, …), product-management(write-spec — order 자체가 쓴다).
- 방식: 라이브러리마다 스킬 이름·설명만 모은 카탈로그를 만들고, init이 인터뷰 내용과 맞춰 레인별로 몇 개만 고른다. 고른 스킬은 프로젝트 `.claude/skills/`에 복사하고 출처·라이선스 표기(Apache-2.0 NOTICE)를 남긴다. 다른 라이브러리(Jin의 스킬 등)도 같은 방식으로 꽂을 수 있게 한다.
- 선: 다 깔지 않는다(설명만으로도 컨텍스트를 차지). 효과는 on/off 비교로 잰다(재작업 PR 비율, 질문 수).
- 순서: P8.

### D24. 실행기의 일시 오류는 실패로 세지 않는다 (2026-10-20, 구현 중 실제 발생)
- 계기: Codex가 "Selected model is at capacity"로 두 번 연속 중단. 사용자 한도가 아니라 모델 서버 쪽 일시 포화.
- 결정: runner는 실행기 출력에서 일시 오류(모델 용량 초과, 과부하, 연결 끊김)와 한도 오류(사용량·요율 한도)를 구분한다. 일시 오류는 시도 횟수를 쓰지 않고 지수 대기(예: 2·4·8분) 후 같은 시도를 다시 한다. 한도 오류는 그 레인을 멈추고 한도가 풀릴 때까지 기다린다(멈춤으로 판정하지 않음, gate.md 8장). 대기 상한을 넘기면 tech-failure로 사람에게.
- 선택: 설정으로 대체 모델(`executor_fallback_model`)을 두면 일시 오류가 계속될 때 그 모델로 넘어간다. 기본은 없음(품질이 바뀌므로 명시적으로만).

### D25. 화면에서는 "레인"으로, 일을 먼저 보여 준다 (2026-10-20, Jin)

### D26. 난이도에 따라 실행 등급을 동적으로 (2026-10-20, Jin; delion-wave model-routing에서 가져옴)
- 레인(어디를)과 난이도(얼마나 센 머리가)는 다른 축이다.
- 결정: order가 이슈마다 `size:s|m|l`을 매긴다(승인 표에서 사람이 바꿀 수 있음). 설정 `tiers`가 등급별 실행기·모델·추론 강도를 정한다(모델은 계속 바뀌므로 코드에 박지 않는다). gate는 이슈 크기에 맞는 등급으로 시작하고, 시도가 실패하면 다음 시도를 한 단계 위 등급으로 올린다(상한 = 최상 등급). 레인 설정의 실행기·모델이 있으면 레인이 우선하고, 난이도는 그 안에서 추론 강도만 조정한다.
- 이유: 처음부터 비싼 모델을 쓰지 않고 필요할 때만 올린다 — 빠르고 싸다. 실패가 곧 난이도 신호다.
- 순서: P8과 함께.

### D27. 타깃 사용자와 최적화 기준 (2026-10-20, Jin)

### D28. 기존 프로젝트에 들이기(brownfield) (2026-10-20, Jin)
- 계기: init을 빈 폴더 전용으로만 생각했지만, Foragent 없이 개발하던 사람이 중간에 들이는 경우가 더 흔하다. Foragent 저장소 자체가 첫 사례다.
- 결정: `/fa-init`이 빈 폴더인지 기존 프로젝트인지 스스로 판별한다. 기존 프로젝트면: (1) 코드 구조와 git 기록(자주 바뀐 경로)으로 레인을 제안, (2) 열린 이슈를 가져와 order가 Done when·인수 시험을 붙여 계약 형식으로 다시 쓴 뒤 승인, (3) 기존 `.claude/`·CLAUDE.md·스킬·CI는 건드리지 않고 필요한 것만 더함, (4) 기준 테스트를 한 번 돌려 이미 깨진 테스트를 알려 줌(깨진 기준선에서는 판정이 애매해짐).
- 참고: Ouroboros에도 `ouroboros-brownfield`가 있다(같은 문제 인식).
- 순서: Foragent 저장소에 현재 init으로 최소 설정 → 이 기능을 Foragent 첫 주문으로 넣어 Foragent가 스스로 만들게 한다(dogfooding).
- D28 보강 (dogfooding 첫날 발견): order는 인수 시험을 구현 전에 main에 넣으므로, 그 시험들은 구현 전까지 일부러 실패한다. 프로젝트 CI가 인수 시험 폴더까지 돌리면 모든 PR의 CI가 다른 이슈의 미구현 시험 때문에 실패하고 gate가 멈춘다. init(특히 기존 프로젝트)은 CI가 `acceptance_dir`를 제외하는지 확인하고, 아니면 제외하도록 제안·수정한다. 인수 시험은 gate가 이슈별로 해당 파일만 직접 실행한다.
- D28 보강 (Jin): 기존 문서가 인터뷰를 줄인다. init·order는 묻기 전에 설계 문서·결정 기록·README·CLAUDE.md/AGENTS.md·기존 스펙을 읽고, 정해진 것은 묻지 않고 "문서에서 이렇게 읽었다" 목록으로 확인만 받는다. 인터뷰는 문서에 없는 빈칸만. (Foragent 저장소의 첫 /fa-order는 D1–D28이 있으므로 질문이 거의 없어야 정상 — 많으면 order의 결함.)
- 기존 이슈 정리: 이슈마다 다시 쓰기(계약 형식 + 인수 시험) · 쪼개기 · 합치기 · 닫기 제안(사유와 원문 보존) · 그대로 두기(코드로 끝나지 않는 일)를 제안하고 한 번에 승인받는다. 승인한 것만 실행, 삭제는 하지 않는다.

### D29. 인터뷰 엔진은 바꿔 끼울 수 있게, 기본은 Ouroboros (2026-10-20, Jin)— 구현됨(엔진 설정과 교체). 실제 Ouroboros 설치·시험은 Jin 결정 대기

Ouroboros가 없거나 실패하면 native로 대체. Ouroboros의 run/evolve(실행 루프)는 쓰지 않는다(D18: 작업 안의 반복은 순정 /goal).

- 검증: D27의 A/B/C 비교(가상 사용자)로 native vs ouroboros를 잰다 — 미구현.

### D30. 일이 생기면 바로 깨운다 (2026-10-21, Jin)
- 문제: gate는 launchd 5분 주기로만 깨어나서, 승인 직후 최대 5분, 그리고 이슈 하나가 끝날 때마다 다음 이슈까지 최대 5분을 기다렸다. "끝나면 바로 다음 일을 가져온다"는 핵심 가치와 어긋나고 처리량을 잃는다.
- 결정: 일이 생기는 순간 곧바로 tick을 분리 실행한다 — `fa order publish --approve` 직후, runner가 run을 끝낸 직후(어떤 결과든), `fa inspect retry`/`answer` 직후, `fa gate install` 직후. tick 잠금이 겹침을 막는다. launchd 5분 주기는 놓친 것을 잡는 안전망으로 남긴다.

### D31. GitHub Projects 보드를 화면으로 (2026-10-21, Jin)— 구현됨 (2026-10-22)
- 발견: 이슈 발행과 Projects 보드는 별개다. 지금 Foragent는 보드를 만들지 않아 D25의 "레인별 줄 칸반"이 없다.
- 결정: init이 프로젝트 보드(Projects v2) "Foragent: <repo>"를 만들고 필드 Lane(단일 선택), Size(s/m/l), Status(Approved/Ready/Running/Needs human/PR open/Done)를 둔다. order는 이슈를 만들 때 보드에 넣고 Lane·Size를 채운다. gate는 상태 전이마다 Status를 갱신한다(한 방향). 보드를 Lane으로 묶으면 레인별 줄이 된다 — "레인에 쌓인 이슈를 하나씩 쳐내는 화면"을 GitHub가 그려 준다.
- 원칙: 진실은 이슈 라벨. 보드는 보기용이라 어긋나거나 지워져도 시스템은 돈다. 보드 갱신 실패는 tick을 막지 않는다.
- 만드는 방법: Foragent 저장소에서 /fa-order로 주문(dogfooding 두 번째 주문).

### D39. 리뷰 범위는 PR 본문의 "Review scope"로 (2026-10-21, Jin 제안 + 비교 실험)— 구현됨(`review_scope` 선택 가능, 기본 claude-local). 두 방식 비교는 D27과 함께
- 문제: 순정 /code-review가 이슈 범위를 몰라 사소한 개선·다른 이슈의 잠긴 시험 실패까지 결함으로 내서 큐가 멈춤(#2·#7).
- 비교(같은 #7 변경): (A) worktree의 임시 CLAUDE.local.md에 이슈 본문 + "이것만 막아라" 규칙 + low → 지적 1개(진짜 결함), 13초. (B) `/code-review <PR> low`(규칙 없음) → 리뷰어가 연결된 이슈를 스스로 읽었지만 지적 4개 이상, 테스트 286개를 직접 돌려 1분 40초, PR 본문의 지난 리뷰 지적에 영향 받음.

- 현재: 큐를 풀기 위해 (A)를 blocker 수정으로 먼저 적용. (A)와 PR+규칙 방식을 실제 이슈들로 비교한 뒤 정한다(지적 수, 진짜 결함 비율, 시간).

### D42. 리뷰 결과는 두 단계로 정리한다 (2026-10-21) — 대체됨(D44): 애매한 리뷰는 원문 그대로 레인 에이전트에게 넘긴다

### D44. 문제는 가장 가까운 층이 먼저 푼다 (2026-10-21, Jin)— 구현됨 (2026-10-22)
- Jin의 질문: gate는 LLM 없는 스케줄러지만 레인 에이전트(구현자)는 LLM이다. 오늘 멈춘 문제 중 일부는 그들이 풀었어야 하지 않나?
- 결정: 문제가 생긴 층에서 가장 가까운 LLM이 먼저 푼다.
  - 이슈 안의 일 → 레인 에이전트: 리뷰 판정이 애매하면 runner는 멈추지 않고 리뷰어 원문을 그대로 구현자의 다음 시도에 넘긴다(형식이 무엇이든 LLM이 읽는다 — 해석기 두더지 잡기와 D42가 필요 없어진다). 구현자는 지적마다 고치거나 "범위 밖·결함 아님 + 이유"로 답할 수 있고, 그 답은 PR에 기록되어 다음 리뷰어(새 세션)가 보고 다시 판정한다(하는 쪽과 판정하는 쪽의 분리는 유지 — 구현자가 판정을 대신하지 않는다). 같은 지적에서 두 라운드 계속 맞서면 오케스트레이터로.
  - 시스템 차원의 일(설치본, gate 규칙·분류, 레인 사이 충돌·병합, 반복 실패) → 오케스트레이터(D43).

- 기대: 2026-10-21 멈춤 중 리뷰 형식(3번)·범위 모르는 지적은 레인 에이전트 층에서, 예전 설치본·재시도 분류는 오케스트레이터 층에서 풀린다.

### D47. 레인 이름은 둘: 기계용 slug와 사람용 이름 (2026-10-21, Jin)— 구현됨 (2026-10-22)

- 계기: Foragent 자체를 개발할 때 머지 뒤 `uv tool install --force --reinstall .`을, 진행을 보려면 `fa gate watch`를 사람이 직접 쳐야 했다. Jin: "사람이 그렇게 명령어를 쳐야 한다고?"

  1. **재설치:** 오케스트레이터가 머지할 때(D46), 머지한 저장소가 Foragent 자신이면 재설치와 "설치본 = 소스" 확인까지 이어서 한다. 사람은 머지 질문에서 "머지해"만 고른다. 일반 사용자에게는 해당 없다.
  2. **레인 화면:** `/fa-order`가 주문을 발행하거나 오케스트레이터 세션이 시작되면 레인 화면이 저절로 열린다. Orca 안이면 옆 칸으로 나눠 띄우고(`orca terminal split`), 일반 터미널이면 새 창을 연다. 이미 열려 있으면 다시 열지 않는다.
- 원칙: 사람에게 명령어를 안내하는 문장은 실패 신호다. 안내 대신 Foragent가 실행한다.
- D57 보강 (2026-10-22, Jin: "레인이랑 에이전트가 생기면 TUI가 뜨는 게 좋다"): 레인 화면을 여는 때를 넓힌다. **레인이 생길 때**(`fa init`이 레인 있는 설정으로 끝날 때, `fa lanes add`, `/fa-order` 발행으로 레인이 만들어질 때)와 **에이전트가 일을 시작할 때**(실행기가 이슈를 잡을 때) 모두 연다. 이미 열려 있으면 다시 열지 않는다. 여는 방법은 위 2와 같다(Orca 안이면 옆 칸, 아니면 새 창). 계기: `/fa-init`을 돌린 Jin이 init 뒤에 화면이 쪼개지고 TUI가 뜰 거라 기대했다.
- D57 보강 2 (2026-10-22, Jin: "세로로 나누는 게 훨씬 좋다"): Orca에서 나눌 때는 `orca terminal split --direction vertical`(작업 칸 옆에 나란히)로 연다. `horizontal`(위아래)은 쓰지 않는다. 두 방향을 직접 띄워 비교한 뒤 정했다.
- D57 보강 3 (2026-10-22, Jin: "다 세로로 쪼개는 걸 기본값으로"): Orca 말고도 칸 나누기를 명령으로 시킬 수 있는 터미널(tmux, iTerm2, WezTerm, Kitty)이면 그 안에서 칸을 나눠 연다. 모두 작업 칸 옆에 나란히(세로 경계선)가 기본이다. 칸 나누기가 없는 macOS 기본 터미널만 새 창으로 연다(사용자가 적어 그것으로 충분). 어느 터미널 안인지는 환경 변수 같은 사실로 판정한다. 아직 미구현: 다음 주문에 넣는다.

### D58. 인터뷰는 Ouroboros 설계를 가져와 native로 돌리고, 그 위에 레인을 얹는다 (2026-10-22, Jin) — 미구현
- 계기: Ouroboros(Q00/ouroboros)와 가재코드(Yeachan-Heo/gajae-code)의 인터뷰를 뜯어봤다. 가재코드는 Ouroboros 인터뷰를 자기 코드로 옮겨 기본 탑재했고(`deep-interview ouroboros ooo-interview parity port` 테스트), 진짜 Ouroboros 연결은 사용자가 따로 설치하는 선택 사항이다. 두 도구에는 공통 문제가 둘 있다. (1) 문서로 남긴 결정을 다시 묻는다. 질문자가 문서를 못 보고(Ouroboros MCP 질문자는 도구 없이 대화만 본다), 지식을 "코드 사실"과 "이번 인터뷰의 답"으로만 나눠서 "예전에 내려 문서로 남긴 결정"이 들어갈 칸이 없다. (2) 인터뷰가 요구사항 스펙에서 끝난다. Foragent는 레인과 스킬까지 정해야 한다. Jin이 반대 방향의 문제도 짚었다: 상황이 바뀌어 다르게 하고 싶은데 옛 문서를 끌고 와서 안 된다고 막는 것.
- 결정:
  1. **기본 엔진은 native.** Ouroboros는 선택 사항으로 남긴다(D29의 "기본은 Ouroboros"를 대체). 가재코드와 같은 배치.
  2. **Ouroboros에서 가져올 설계:** 큰 그림(덩어리)을 먼저 확인받고, 가장 흐릿한 칸부터 한 번에 한 질문, 자유 답은 "결정 / 이유 / 제약 / 안 할 것"으로 정리해 확인(Refine), 항목마다 출처 표시(코드 / 문서 / 사람 / 가정), 빈칸이 남으면 끝내지 않는다.
  3. **결정 장부:** 문서에 남긴 결정은 "예전에 받은 답"이다. 묻기 전에 문서를 읽어 장부를 만들고(항목마다 출처와 날짜), 한 번에 보여 주고 확인받는다. 이후 질문은 장부의 빈칸만 다룬다.
  4. **지금 하는 말이 문서를 이긴다.** 문서는 사용자가 말하지 않은 곳을 메울 뿐, 사용자를 막는 근거가 아니다.
     - 사용자가 바꾸겠다고 말하면: 막거나 설득하지 않는다. "바꿔도 되나"를 묻지 않는다. 그 결정에 기대는 다른 결정과 열린 이슈(파급)만 보여 준다.
     - 요청이 문서와 부딪히는데 사용자가 바꾼다고 말하지 않았으면: 한 번만 묻는다. "D18은 X인데 이번 요청은 Y입니다" — 바꾼다 / 예전대로 / 이번만 예외.
     - 바꾸기로 했으면 주문과 함께 결정 기록을 고친다(새 항목 + 옛 항목에 "대체됨"). 기록하지 않으면 레인 에이전트가 계속 옛 문서를 읽고 막는다.
  5. **레인을 얹는다:** 덩어리마다 칸 다섯 개 — 목표, 안 할 것, Done when, 레인, 스킬 — 가 다 차야 인터뷰가 끝난다. 레인(코드 경로·기존 레인 기준)과 스킬(`fa skills catalog` 기준)은 에이전트가 채우고, 새 레인이 필요하거나 담당이 애매하거나 맞는 스킬이 없을 때만 선택지를 붙여 묻는다. "맞는 스킬 없음(이유)"도 답이다. 이 표(레인 지도)는 인수 시험을 쓰기 **전에** 확인받는다. D56 2의 별도 팀 인터뷰는 이 인터뷰에 합친다.
  6. **빈칸 세기는 코드가 한다:** `fa order publish`가 칸이 빈 이슈를 거절한다. 판단이 아니라 사실 확인이다.
  7. **팀 인터뷰는 따로 두지 않는다(D56 2 대체).** 프로젝트 성격(랜딩인가 매일 쓰는 앱인가, 만드는 단계인가 다듬는 단계인가, 지금 속도·생김새·안정성 중 무엇이 중요한가)은 첫 주문 인터뷰에서 한 번 묻고 장부에 적는다. 다음 주문부터는 장부가 답하고, 레인에 스킬을 달 때 근거로 쓴다.
  8. **장부에는 '결정'과 '현재 상태'가 있다.** 결정은 누가 바꾸기 전까지 그대로다. 현재 상태(단계, 우선순위)는 프로젝트가 크면서 아무도 선언하지 않아도 바뀐다. 그래서 현재 상태는 사람이 `/fa`로 세션을 시작할 때 **한 번만 확인한다**(D59) — "지금 우선순위: 속도 (10/01 기준), 그래서 디자인 검토는 빼고 시험은 핵심 흐름만 넣고 있습니다. 그대로 갈까요?"처럼 그 상태 때문에 무엇이 달라지는지를 함께 보여 준다. 주문마다 다시 묻거나 보여 주지 않는다. 바뀐 것 같은 근거가 보이면(예: 최근 주문이 대부분 버그 수정) 에이전트가 먼저 바꾸자고 제안한다. 주문 하나만 다르게 갈 수도 있다(전체는 안정성 우선, 이번 랜딩 손질만 생김새 우선).
- 가져오지 않는 것: LLM이 매긴 모호도 점수와 문턱(자기평가라 숫자의 정밀도는 착시), 가재코드식 세부 금지 규칙(똑똑해진 모델을 묶는다), "AI가 3번 연속 답하면 사람에게"(문서로 답할 수 있는 것을 억지로 묻게 해서 (1)을 만든다).
- 검증: Foragent 저장소의 주문은 질문이 거의 없어야 정상이다(D28 보강). 장부와 부딪히는 요청을 넣었을 때 막지 않고 한 번만 묻는지, 바꾼 뒤 결정 기록에 대체가 남는지 본다. native와 Ouroboros 비교는 D27로.
- 구현 때 정할 것: 결정 기록이 없는 저장소에서 장부를 어디에 남길지, 대체 기록을 주문 이슈로 할지 발행 때 직접 고칠지.

### D59. 입구는 `/fa` 하나: Foragent가 상태를 보고 할 일을 고른다 (2026-10-22, Jin) — 미구현
- 계기: Jin: "사람이 'fa init, order 중에 뭘 해야 하지?'라고 고민하게 하면 안 될 듯. 걍 `/fa` 하면 알아서 되게." D57 원칙(사람에게 명령어를 안내하는 문장은 실패 신호)을 입구에도 적용한다.
- 결정: 사람이 치는 스킬은 `/fa` 하나다. `/fa`는 상태(사실)를 보고 다음 흐름으로 이어 간다.
  1. 이 폴더에 Foragent 설정이 없으면 → 설정(`/fa-init` 흐름).
  2. 사람이 봐야 할 것(검수함·결정 대기·사람 호출)이 있으면 → 점검(`/fa-inspect` 흐름)부터. 끝나면 "다음에 무엇을 만들까요?"로 이어진다.
  3. 둘 다 아니면 → 주문(`/fa-order` 흐름).
- 기존 `/fa-init`·`/fa-order`·`/fa-inspect`는 직접 부를 수 있게 남기되, 안내 문장에는 `/fa`만 쓴다.
- 같은 날 발견한 구멍(D57 1 재설치): #93은 `fa orch merge`로 머지할 때만 재설치한다. `review: fast`에서 gate가 스스로 머지할 때는 재설치하지 않는다. 다음 주문에 "gate 자동 머지 때도 재설치"를 넣는다.

- D59 보강 (2026-10-22, Jin: "fa를 하면 현재 진행상황, 어떤 레인에 어떤 에이전트들이 셋업되어 있는지 쫙 정리가 되면 좋을 듯"): `/fa`는 흐름을 고르기 전에 **시작 브리핑**을 먼저 보여 준다. 네 부분:
  1. **지금 일하는 중:** 레인별로 무엇을 하고 있는지, 어느 단계인지, 얼마나 됐는지. 순서를 기다리는 이슈.
  2. **볼 것:** 사람이 처리할 것(리뷰, 사람 확인, 결정 대기)과 예상 시간.
  3. **팀 구성:** 레인, 작업자(실행기), 레인마다 달린 스킬. 빈 곳(스킬 없는 레인 등)은 ⚠로 드러낸다.
  4. **현재 상태 확인:** D58 8의 우선순위·단계 확인을 여기서 한 번 한다.
  마지막에 다음 할 일을 추천과 함께 고르게 한다(예: 볼 것 처리 / 새로 주문 / 레인·스킬 정리).
  - 나누기: 사실(진행, 레인, 스킬, 볼 것)은 명령어 하나가 모아 낸다(재료는 지금 `fa gate status`와 `fa inspect`에 흩어져 있다). 요약과 "무엇부터 할지" 추천은 에이전트가 한다 — 코드에 규칙으로 넣지 않는다.
  - 처음 그려 보니 Foragent 저장소의 레인 8개 모두 스킬이 비어 있었다. 이런 빈 곳이 시작 화면에서 바로 보이는 것이 브리핑의 쓸모다.

### D60. 요금제 한도와 컴퓨터 성능이 허락하는 만큼 밀어붙인다 (2026-10-22, Jin) — 미구현
- 계기: 동시 실행 수 `max_parallel`이 고정 2라서 할 일이 있는 레인도 기다린다. Jin: "토큰이 개발력인 세상이고, 이걸 쓰는 사람은 토큰 한도를 태우려고 쓰는 것에 가깝다. 한도에 닿으면 어차피 개발이 멈춘다." Jin은 이전에 세션 6~7개를 하루 종일 직접 관리했다 — Foragent가 대신해야 할 일 그 자체다.
- 결정:
  1. **동시 실행 수는 컴퓨터 성능으로 AIMD(덧셈으로 늘리고 곱셈으로 줄이기)를 한다.** 메모리 압박이 보통이고 CPU에 여유가 있으면 천천히 +1, 빠듯해지면 바로 절반. 상한은 할 일이 있는 레인 수. 컴퓨터 성능은 리셋되지 않는 진짜 한계라서 지킨다. 측정은 macOS `kern.memorystatus_vm_pressure_level`·`vm.loadavg`, 리눅스 `/proc/pressure`·`/proc/loadavg`.
  2. **요금제 한도는 막힘이 아니라 목표다.** TCP식으로 물러서지 않는다(아낀 몫은 리셋 때 사라진다). 실행기 출력에서 사용량과 리셋 시각을 읽는다 — Claude `rate_limit_event`(`utilization`, `resetsAt`, 5시간·7일), Codex `rate_limits`(`used_percent`, `resets_at`). 한도에 닿으면 그 실행기 전체를 리셋 시각까지 쉬게 하고, 리셋되면 바로 전속력으로 다시 돌린다.
  3. **안전선:** 사용량 필드는 공식 약속이 아니다. 못 읽으면 지금 방식(`limit_wait_minutes` 뒤 다시 시도)으로 돌아간다. 깨져도 멈추지 않는다.
  4. **Claude는 모드 두 개:** "다 태우기" / "내 몫 남기기"(레인은 한도의 80%까지 — 같은 구독을 쓰는 사람의 대화 세션 몫). 사람마다, 날마다 다르므로 숫자를 고정 설정으로 묻지 않는다. 처음은 `fa init`에서 한 번 묻고, 기본 숫자는 설정에서 바꿀 수 있다. Codex 등 남는 쿼터는 끝까지 태운다.
  5. **보이게:** 레인 화면(TUI) 맨 아래 상태 줄에 사용량·리셋 시각·메모리·동시 실행 수·모드를 띄운다. 일이 없으면 숫자가 새로 오지 않으므로 기준 시각을 함께 쓴다("41% · 10분 전"). `m` 키 하나로 모드를 바꾼다(레인 화면이 받는 유일한 입력). `/fa` 시작 브리핑(D59 보강)은 같은 줄을 보여 주기만 하고 묻지 않는다.
- 원칙: 측정값으로 하는 계산과 안전선이다. "지금 무엇을 할지"는 넣지 않는다.
- 구현 때 정할 것: AIMD의 늘리는 간격(작업 하나가 몇 분에 걸쳐 메모리를 늘린다 — 시험으로 맞춘다), 7일 한도가 5시간 한도보다 먼저 닿을 때의 표시.

### D61. Foragent의 말투: 토스 UX 라이팅 5원칙 + STE를 한 장으로 (2026-10-22, Jin) — 미구현
- 계기: `/fa` 브리핑의 전달 방식을 다듬다 확인해 보니, 지금 Foragent에는 말투 기준이 없다. Jin의 짧은 문장·쉬운 말(ASD-STE100)은 Jin의 개인 설정(`~/.claude/CLAUDE.md`)에만 있어서 Jin의 Claude 세션만 따른다. 레인 실행기(Codex)도, 오픈소스로 쓰는 다른 사람도 그 기준을 받지 못한다. D33의 `docs/design/CONTRACT.md`는 사용자가 만드는 제품의 기준이라 Foragent 자신의 말투를 둘 곳이 아니다.
- 결정: Foragent가 사람에게 하는 모든 말(스킬 대화, 시작 브리핑, TUI, 알림, 이슈·PR 문구)은 한 장짜리 말투 기준을 따른다.
  - **공통:** 능동형("Foragent가 머지했어요", "Foragent merged the issue"), 긍정형 — 안 되는 것보다 할 수 있는 것과 해결책을 말한다("다시 시도하면 연결돼요", "Retry to reconnect"), 명사 나열 금지("계좌 등록 완료" → "계좌를 등록했어요", "Account registration complete" → "You added your account"), 짧은 문장, 쉬운 단어, 한 문장에 하나.
  - **한국어만:** 해요체, 과한 높임(`~시`, `께`, `여쭈다`) 빼기.
  - **영어만:** 대화체, 줄임말 허용(you're, it's), 딱딱한 공손 표현("Please kindly be advised") 빼기.
  - 예외는 토스 가이드를 따른다: 종료·만료·사용자에게 미치는 영향은 수동형을, 정책상 못 쓰는 경우는 부정형을 쓸 수 있다.
- 넣을 곳: 사람에게 말하는 스킬(`/fa`, `/fa-order`, `/fa-inspect`)의 짧은 말투 절, TUI·알림 문구(i18n 문자열)를 이 기준으로 고친다. view 레인에 토스 UX 라이팅 스킬(NariP/toss-ux-writing-skills, MIT, 출처 토스 공식 가이드)을 단다 — Foragent 레인의 첫 스킬 장착 사례다.
- 출처: 토스 앱인토스 UX 라이팅 가이드(developers-apps-in-toss.toss.im/design/ux-writing.html), ASD-STE100. 토스의 원칙을 빌릴 뿐 토스 브랜드를 쓰지 않는다.
