# fa-inspect (검수) — 설계 초안

> 2026-10-20: `morning`에서 이름을 바꿨다(D15). 시간과 무관하다. 사람이 자리를 비웠다 돌아와서 실행한다.

상태: 초안 (2026-10-20). 결정 대기 항목은 맨 아래.

## 하는 일

사람이 없는 동안 gate가 남긴 결과를 모아, 사람이 **30분 안에** 처리할 수 있게 보여 주고, 사람의 답을 GitHub에 남긴다. 그 답은 다음 order의 입력이 된다.

inspect는 새 판단을 하지 않는다. gate가 GitHub에 남긴 상태(라벨, 댓글, PR)를 읽고, 사람이 행동할 순서로 정리할 뿐이다.

## 1. 무엇을 보여 주나 — 사람이 할 행동 순서로

| 순서 | 묶음 | 출처 | 사람이 하는 일 |
|---|---|---|---|
| 1 | **결정** | `needs-human` 중 스펙·제품 판단이 필요한 것 | 선택지 중 하나 고르기 |
| 2 | **재승인** | 본문 해시 불일치로 멈춘 이슈 | 바뀐 본문을 보고 다시 승인 |
| 3 | **검토** | `careful` PR, `batch` 묶음, `always_human`·시험 파일을 건드린 PR | 머지 또는 거절 |
| 4 | **사람 확인** | PR 본문의 체크리스트(기계로 못 한 확인) | 써 보고 체크 |
| 5 | **써 보기** | 사람이 없는 동안 머지된 것 | 링크나 명령으로 직접 써 보기. "이게 아닌데"는 피드백으로 |
| 6 | 참고 | 완료 수, 실패 원인 통계, 사용량 | 읽기만 (짧게) |

- 1~4는 **사람이 해야 다음 일이 풀리는 것**이라 먼저 보여 준다.
- `needs-human` 중 단순 기술 실패(재시도 초과)는 "결정"이 아니라 정보와 함께 보여 준다: 실패 출력 요약 + 추천("이슈를 쪼개서 다시 order" / "그냥 다시 시도" / "버리기").

## 2. 항목 하나의 모양

항목마다 링크를 열지 않아도 판단할 수 있어야 한다.

```
[결정] #42 결제 실패 시 재시도 횟수
  왜 멈췄나: 스펙에 재시도 정책이 없음. 구현자가 3회/무제한 중 고르지 못함.
  선택지:  ① 3회 후 실패 안내 (추천: 일반적, 비용 예측 가능)
           ② 사용자가 직접 재시도
  링크: github.com/.../issues/42
```

## 3. 한 번에 30분 예산

- 항목이 많으면 **결정과 재승인을 먼저** 보여 주고, 나머지는 "오늘 못 본 것"으로 내일로 넘긴다. 넘긴 것은 사라지지 않는다(GitHub 상태 그대로).
- 매일 결정 항목이 많다면 order가 이슈를 덜 명확하게 쓰고 있다는 신호다. inspect는 이 통계를 다음 order에 넘긴다. 예: "어제 막힌 5건 중 3건이 Done when 부족".

## 4. 답을 남기는 방법

사람의 답은 모두 GitHub에 남는다 (contract 5번: 진실은 GitHub 한 곳).

| 답 | GitHub에 남는 것 | 다음에 누가 읽나 |
|---|---|---|
| 결정 | 해당 이슈에 댓글 | order (그 이슈의 Done when·본문을 고침 → 재승인) |
| 피드백("이게 아닌데") | 새 이슈 + `feedback` 라벨 | order |
| 재승인·머지 | 승인 PR 머지 / PR 머지 (사람 신원, Q1) | gate |

결정과 피드백은 **입력**이지 승인이 아니므로 봇 신원으로 남겨도 된다. 승인과 머지만 사람 신원이 필요하다(Q1).

## 5. 알림

- 처리할 것이 생기면 프로젝트 창구로 **한 줄**만 보낸다: "오늘 결정 2 · 재승인 1 · 검토 3 · 써 보기 5".
- 내용은 알림에 다 담지 않는다. 알림은 "열어 볼 때가 됐다"는 신호다.
- 처리할 것이 0이면 보내지 않는다.
