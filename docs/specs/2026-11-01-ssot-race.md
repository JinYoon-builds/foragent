# Preserve the public evidence of accepted retry and talk advice

## Goal and ownership

An accepted retry hint or talk message keeps a verbatim issue-owned copy through concurrent workflow writes, local prompt delivery, GitHub deferral and later gate delivery. With a writable backend, the existing locked retry/talk test must finish with both messages in the issue body or real comments. With a temporarily unavailable backend, acceptance requires a durable publication intent that survives later label/state observations and reaches a real comment after recovery. The comment is delivered once.

One issue, `accepted-advice-publication`, size `s`, lane `board`, no blockers. The lane map in `.foragent.yml` assigns `src/foragent/tracker.py` to `board`; that transport determines whether the advice is sent or queued. The associated store and advice-producer files belong to the same repair. This order is a draft: source implementation is the downstream lane's work.

## Root cause

This is a product publication race. `orch._retry` and the talk CLI persist public evidence through `orch_advice.publish` before adding deliverable local hints. `run_previous.add_hint` serializes appends and `consume_hint` removes only the delivered prefix; the reproduced loss is in public evidence, not the hint queue.

`RecordingTracker._write` can queue a comment behind an in-flight issue-field intent. `queue_github_write` attaches the current issue premise to that comment. `state_observations.retirement` then treats its changed labels or open/closed state like a reason to discard a superseded workflow write. There is no lifetime distinction between the durable evidence of accepted advice and a cancellable transition announcement.

A controlled run pauses only the fake GitHub label send. The talk command accepts its message while that send is pending. The captured comment intent has id 2, verbatim talk text and premise labels `approved, blocked, ready`. The fake label acknowledgement also sees `running`, which the locked fixture adds to simulate the new run. The locked fixture gives the concurrent operations the same fixed timestamp, so that acknowledgement is eligible to retire the accepted comment as a remote change. The separate public-CLI recovery case advances the clock between publication and observation, proving that accepted-evidence loss also occurs with strictly ordered timestamps. The test later consumes both hints and fails with no pending publication and no talk comment. A subsequent real scheduler tick with a fresh StateStore has nothing to retry. A separate public talk-CLI case reproduces the same loss after a real simulated human label event and transport recovery, without the locked fixture's concurrent start.

The 2-second and 3-second waits select an interleaving; they do not explain away lost durable state. Both producer futures have completed before the original public assertion. Increasing waits, waiting for comments after they were discarded, or adding a test-only flush cannot restore the missing publication.

## Required behavior

- A writable issue backend receives both accepted messages despite concurrent label writes. The existing public issue/comment assertion remains intact.
- An accepted publication deferred by GitHub errors or waits remains recoverable for an existing issue as its labels/state evolve; prompt acknowledgement cannot erase its public evidence. A later gate tick delivers it exactly once.
- Retry and talk still append both undelivered messages. A late message survives acknowledgement of the earlier prompt. Delivered advice is absent from the second prompt, and the existing no-real-GitHub assertion remains intact.
- Ordinary superseded workflow writes and their transition announcements still respect a person's newer state. Evidence delivery does not overwrite labels or reopen/close the person's issue. Preserve the existing missing-issue behavior.

The production change concerns structured publication lifetime and transport facts. Payload meaning, keyword/marker classifiers, LLM decisions inside scripts and new agent execution orders are outside this issue.
