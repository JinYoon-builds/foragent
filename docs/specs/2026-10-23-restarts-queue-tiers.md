# Fewer restarts, ordering without fake dependencies, and measured phases

Evidence (2026-10-23): #138 stopped three times on spec questions; each retry started a fresh worker and lost 15-85 minutes. The orch lane sat idle for 8 hours because the orchestrator ordered issues with blocked_by links that were not real dependencies. Acceptance baselines took 128 s idle, ~540 s with four runs and 851 s at peak (machine contention, 8 CPUs / 16 GB); the scorecard needs phase times and load to tell these apart.

1. resume-after-question: after a `spec-question` stop, an edited and re-approved issue resumes the same worker session (`codex exec resume <id>` / `claude --resume <id>`, ids recorded by #153) with only the changed spec text and the orchestrator's answer. No session id, or a failed resume: start fresh with the full prompt as today. Other retries are unchanged.
2. order-preread: `fa order preread PLAN.json [--json]` has the configured implementer read each issue's plan and acceptance tests read-only and list unknowns (or `NONE`). `fa order publish --approve` refuses until the latest preread of this exact plan content has no unknowns. `--dry-run` is never blocked. The orchestrator answers unknowns; only D71 questions go to the person.
3. lane-queue: `fa orch queue <lane> <n>...` stores a lane's preferred order locally; the tick starts the first startable issue in that order, then unqueued issues by number. Real blocked_by always wins; a blocked queue head keeps its place while the next one runs. The program never reorders by itself (D71: the orchestrator decides).
4. model-depth-choice (D74 addendum 1): both executors get per-size model and depth fields; ample quota headroom (default 0.5 left, `tiers_headroom_ample`) runs s and m issues at the l tier; tight headroom uses each size's tier; l keeps l; each failure goes one tier up and the last attempt runs highest; an empty model means the executor default.
5. Scorecard additions (#224, #225): a `kind=phase` event per ended phase with seconds and `os.getloadavg()[0]`; the scorecard shows `spec_questions`, `phase_minutes` (median per phase, pooled within the window) and median `load`.
