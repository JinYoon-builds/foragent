# Team mode v1: each person's factory works the issues that person ordered

Order: `2026-10-30-team-mode-v1`. Decision by Jin, 2026-10-30.

## Why
Teammates each use their own Claude Code subscription, machine, gate, local state,
and orchestrator against one shared product repository. The goal is each person's
own development capacity. There is no team-wide pool of subscriptions or workers.
Conflicts between people's changes are acceptable and go to the existing agent
resolve path. D78's claim-first assignment was for a different allocation policy.

## Root cause and existing parts to reuse
`order.publish` creates lane/size labels and parent/child plan markers, but no
orderer. `scheduler._tick_locked` sees the whole issue listing and admits work
without a person boundary. Local run/process ownership is useful but does not say
which person's factory may operate on a GitHub issue. Orchestrator actions likewise
have no orderer check. A foreign row must remain visible; filtering the listing at
the transport boundary would hide dependencies and planning overlap facts.

Reuse FakeTracker/RecordingTracker, the snapshot and budget work (#138/#221/#139),
approval/body/acceptance integrity, normal PR publication, process identity checks,
WIP preservation, local FIFO #712, overlap measurement, and existing resolve work.
Do not copy the earlier 17-issue claim/lease, quota arbitration, or question-transport
design. `team-mode-17-findings.md` is evidence, not the new allocation contract.

## Decisions and contracts
1. **Orderer truth is one `by:<login>` label.** Use lowercase GitHub login equality.
   Labels are already in bulk tracker reads and local issue rows, including closed
   rows; no extra per-issue read or marker parser is needed for admission. Keep the
   existing plan markers for idempotent publication, not a second owner authority.
   Add `Tracker.authenticated_login()` and delegate it through RecordingTracker.
   GhTracker obtains JSON from `gh api user`, persists the host/account's login in
   the existing machine-local data root, and reuses it across repos/processes.
   FakeTracker supplies an injectable login fact. Re-running fa init refreshes
   and displays the active authenticated identity.
   Cached identity is reusable only for the same host and credential/account context;
   switching accounts or credentials cannot silently retain the previous principal
   for publication or issue effects. If the new principal cannot be authenticated,
   refuse new effects with an actionable diagnostic and keep existing work. Never
   infer it from issue author, Git identity, assignee,
   approver, executor, or the credential used for later approvals. No gh calls in
   render/status paths. Each context projects its successfully authenticated
   login beside the repository snapshot so offline views know whose factory
   they are displaying, including when the tracker boundary is fake in tests.
   An authentication error without a usable cache prevents
   publication/new mutation; it never guesses somebody else's identity.
   Stamp parent and children at initial publication, including unapproved children.
   Lack of permission to create/apply the owner label fails publication visibly;
   no newly created issue may be left unlabelled and eligible as legacy backlog.
   Retrying a partial publication keeps the original owner and avoids duplicates.
   Republishing or approving cannot transfer ownership. Preserve a preexisting
   single owner; refuse contradictory owner labels rather than choosing one.
   Explicit `edits` retain an existing issue's owner; legacy edits remain legacy.
   The skeleton provides `ownership.parse_orderer(labels) -> str | None`
   (one normalized label, none for legacy, OwnershipError for ambiguity),
   `ownership.effective_orderer(issue, config, factory_login) -> str`, and
   `ownership.require_owned(issue, config, factory_login) -> None` (OwnershipError
   for a foreign target). Callers share these names and equality rules rather
   than each building a separate owner parser. The no-setting fallback applies
   only to the unchanged singleton path described below.
2. **Legacy backlog stays with the existing factory.** Add optional repository
   `legacy_owner: <login>` to .foragent.yml. With no setting, the old single-factory
   path is unchanged; existing installations need no immediate migration. Before
   onboarding another person, the original factory records its authenticated login
   here and commits it through its normal PR. A joining factory must have that
   shared setting before it starts: fa init/gate reports the missing setup when
   foreign ownership is already observed without a legacy owner. Missing owner on
   an old issue then means precisely legacy_owner, never 'whoever asks'. Do not
   relabel/reapprove all historical issues. This rollout precondition is needed
   because an unlabelled issue cannot identify its old factory by itself.
3. **Admission and effects share the same person boundary.** An issue with one
   orderer is writable only by that person's factory. Apply this before admission,
   approval/ready/running transitions, recovery/timeout flags, retry attempts,
   issue comments, PR writes, order-parent aggregation, queued-write replay, and
   direct `gate run-issue` execution. Retain all issues as read-only local facts.
   Keep foreign dependencies blocking until they are actually closed. Recheck a
   target's ownership at mutation time. Missing factory identity or ambiguous
   owner labels refuse team effects; an unlabelled issue uses only the specified
   legacy fallback. An own parent may read foreign children but must not mutate them. Do not let foreign backlog consume the person's quota demand.
   This is a cooperative factory-routing boundary, not a GitHub permission boundary.
   With by: as the sole truth, a writer can replace a valid label or remove it
   (making the issue legacy); v1 cannot authenticate that edit or recover its intent.
   Contradictory labels refuse effects. Treat label writers as trusted collaborators
   and repair/correct labels only with affected factories quiescent. Reserve by:
   for orderer logins; resolve an existing namespace collision before onboarding.
   Issue ownership does not prove local process ownership: foreign running labels
   alone never authorize signals. Conversely, scheduler cleanup of a process tree
   this factory demonstrably launched remains possible after an owner edit or
   identity/config failure, with unfinished work retained locally and no new
   unauthorized issue/PR writes or WIP push. A direct foreign stop still refuses.
   Replayed writes use current ownership, including entries queued before upgrade.
   Refused entries remain inspectable with their reason and do not indefinitely
   block unrelated owned writes; they are never silently delivered or discarded.
4. **Orchestrator actions are scoped.** stop, retry, park/unpark, resolve, merge,
   and rerun-review refuse foreign work before checks, executor calls, WIP changes,
   labels, PR changes, journals, signals or outbox writes. Return nonzero and one
   localized line, e.g. `#12 is worked by bob; this factory is alice.` For a PR command,
   resolve its Foragent issue from the existing branch/issue relationship before
   comparing the issue's orderer; do not confuse the PR number with issue number.
   Existing stronger process/approval safeguards still apply to owned work.
5. **Planning receives facts.** `fa order context --json` adds `other_orders`, sorted
   by issue number: `{number, title, orderer, files}` for open non-PR issues owned
   by another person. Files come from the existing structured `## Files` parser;
   missing Files means an empty list, not 'no overlap'. Preserve globs as declared.
   Other context sections remain intact. fa-order SKILL.md tells the planning
   session to show intersections with the person's proposed chunks as facts and
   let that person decide to wait, split files, or go ahead. No keyword judgment,
   similarity threshold, autonomous scheduling decision, LLM inside scripts, or
   agent step-order enforcement is added. Issue questions are posted on that
   issue as a GitHub comment mentioning @<effective-orderer>; their own factory
   planning session presents the question to that person and records the answer
   through the existing issue decision flow. Other factories retain these as
   read-only facts, never questions for their own person. Reuse issue comments
   and existing local planning delivery; add no cross-machine question channel.
   The earlier agent lacked orderer and
   foreign Files context; supplying that context fixes the cause.
6. **Lane memory uses PRs and one dream writer.** Lane workers on every factory
   keep appending memory through the ordinary issue PR path. Add optional
   `lanes.<lane>.dream_owner: <login>` in the shared config. In team mode this is
   the one factory allowed to offer, launch, execute, and publish dreams for that
   lane. If absent, use legacy_owner; in an unchanged singleton, preserve today's
   dream behavior. This stable setting is simpler than electing from order dates
   and does not switch ownership while an old writer is alive. No automatic
   failover or lease. A transfer waits for the old dream/process/PR to finish.
   The separate night order/lane-memory work splitting MEMORY.new.md is independent
   of team mode. An open approved/running work item whose Files overlap this lane's
   memory paths blocks the dream, including a foreign item in a different lane.
   Reuse structural path/glob overlap; do not match issue titles or prose. Recheck
   before launch. Team implementation issues do not change memory contents or the
   splitting format; if an implementation's own Files overlap that other order,
   the planning agent adds the real dependency before approving it.
7. **Status/view stay local and factual.** Preserve foreign issues in the snapshot
   and expose `orderer`, `worked_by`, `read_only` on their rows. Render 'worked by
   <login>' (localized normally) and disable mutations on those rows. Do not present
   foreign work as a stalled local runner or as the person's actionable queue.
   No network call just to render these facts. Show this factory's login and
   identity/setup refusal reason locally, including for unattended gates. Existing
   waiting_for dependency facts retain the foreign blocker number and its owner;
   no invented completion estimate or foreign-machine liveness is implied.
8. **Conflict minutes are measured.** Reuse run_overlap.conflict_resolution's
   clock and waited-time subtraction, but emit one `conflict-resolution` interval
   event per actual resolve attempt, even without a local peer overlap record.
   Fields: stable interval_id, started_at, seconds, paths; event `at` is completion.
   Count the duration once, regardless of file/peer count or event replay. Include
   failed attempts' actual work, exclude slot/overlap waiting, and never infer
   conflict time from total run time. `orch scorecard --json` adds
   `window.today.conflict_resolution_minutes` and the corresponding previous
   daily median, using its existing rolling 24-hour buckets; human output labels
   the unit. A two-file 120-second interval repeated twice counts as 2 minutes.

## Merge-path finding and smallest change
All three production callers have been inspected:
* `run_publish_flow.py` verifies/reverifies implementation work against a fetched
  base and rechecks after the local merge-lock wait.
* `run_publish_reviewed.py` refreshes a changed base and invokes the review-only
  checks before merging an already-reviewed head.
* `orch.merge` performs premerge, takes the local FIFO turn and lock, fetches again,
  and compares the base/head to the checked pair.
`StateStore.merge_lock` and `run_merge_turn.py` use machine-local files. Another
machine does not see that queue. GhTracker.merge_pr currently forwards only
`--match-head-commit`: that condition protects the PR head, not the base. The
adapter has no verified-base input at the last remote mutation boundary. An
offline test returns a new remote base there and today's adapter still merges.

Extend merge_pr with expected_base_sha and carry the base actually covered by
verification through Tracker, RecordingTracker, FakeTracker and all three callers.
GhTracker reads the PR's real target and its fresh remote ref immediately before
the merge request (not origin/main from a local checkout). Refuse if it differs
from expected_base_sha, retain the head match, and return a typed base-moved error.
Never substitute the freshly read SHA as if it had been verified. Missing/unreadable
base proof cannot authorize a real merge. Runner paths refresh/reverify using the
existing unlocked loop and conflict resolve path; orch merge refuses for another
premerge. Keep neutral-base evidence reuse and short lock behavior; a verified
comparison may be reused only under the existing proof rules for the new base.
Remote lookup failure is not base movement: preserve the existing GitHub
rate-limit wait (limit-wait) and other tracker-error/WIP recovery behavior, rather
than sending unavailable proof into the base-moved reverify loop or charging an
implementation defect retry. Repeated actual moves retain the existing run time
budget and neutral-base proof rules; no new retry threshold is added. The orch
refusal identifies that premerge must be run again.
No cross-factory issue claims or merge-lease subsystem is introduced.

Scope assumption: this implements the spec's explicitly offered verified-base
preflight, including movement after the final local fetch. GitHub's merge endpoint
does not offer an atomic expected-base condition: a move between that fresh remote
read and GitHub applying the merge is still a residual race. This plan does not
claim server-side compare-and-swap or solve arbitrary human/third-party merges in
that interval. A strict atomic guarantee needs repository-enforced up-to-date
checks/merge queue or a separate coordinated merge design, beyond this minimal v1.
Document this limit in the shipped spec, not as a hidden guarantee of local FIFO.

## Lane map and delivery
Six normal-size issues use existing lanes only. Identity/publication/config is
the shared skeleton (order). Gate/action scope depends on that contract (orch).
Merge boundary depends on scoped actions and tracker identity plumbing (orch).
Planning facts depend on identity (order). Dream writer depends on scoped gate
and the identity/config contract (orch). Status and conflict-time display depend
on scoped snapshot facts (view). Same-lane work is already serialized; no fake
blocked_by is added for priority. Cross-lane shared config/tracker/order files are
covered by the real identity dependency. Identity owns legacy_owner
validation with its Config change and does not touch config_validation.py.
Only memory owns lanes.<lane>.dream_owner support and validation, including
config_validation.py; do not pre-land that lane setting in identity. Runtime split
modules inherit their
facade's configured lane where .foragent.yml has no explicit path entry.
No new fixed style skills. Implementers choose useful tool/review/domain skills
from each existing lane's approved catalog. All issues are non-interactive.

### D78 revision — each person's factory works that person's orders (2026-10-30, Jin)
Each teammate runs their own factory on their own machine and Claude Code
subscription. For v1, ownership is the person who published the order, recorded
on every published issue as by:<login>. That factory alone admits or acts on the
issue; other factories show it as a read-only fact. Unlabelled historical work
stays with the repository's original factory. This supersedes D78-2/3's
claim-first allocation and the 2026-10-25 per-issue claim/lease addendum for v1.
Keep D78-1 (one product, singleton is a one-person team), D78-5 (GitHub board),
and D78-6 (fa init once). Each person's development capacity is the goal;
cross-person conflicts go to agents to resolve. D78-4's team quota allocation
and atomic ref claims/leases belong to the later, opt-in work-stealing step:
an idle factory may then pull waiting work from other people. They are not v1.

## Out of scope
Spare-capacity work stealing, issue claims/leases/heartbeats, team quota pooling,
assignee-based scheduling, automatic dream failover, shared process state, a
cross-machine question/push transport, and automatic overlap decisions. No change
to order splitting/MEMORY.new.md semantics. No direct-main publication redesign.
Supporting two simultaneous machines with the same person's identity is later
coordination work; v1 has one active factory per person per repository.

## Rollout and recovery
The identity issue extends the existing setup documentation (README.md and
skills/fa-init/SKILL.md), and planning extends docs/order.md; no separate
onboarding system is needed. They explain the active-account refresh via fa init,
legacy routing for hand-created unlabelled issues, reserved by: labels, the
one-factory-per-login limitation, permissions, and normal dream-owner skipping.
The factory identity comes from GitHub authentication, independently of whether
its workers use Claude, Codex, or supported API credentials. An authentication
that cannot provide a human login (for example an App installation token) cannot
order as a guessed person; insufficient repository write/merge permission is a
visible existing failure, not an entitlement granted by by: labels. Cache storage
uses the existing machine data root, not a new macOS-specific path.

2026-10-31 starts with one factory. Merge this order's issues before the first
teammate joins. On the original factory, authenticate/refresh its login, record
legacy_owner and the per-lane dream owners in shared .foragent.yml through a PR,
and wait for old workers/dream PRs before any ownership transfer. All active
factories must run the ownership-aware version before joining; an old fa ignores
the new labels, and upgraded code cannot fence it. A stale checkout does not
define authority: gate uses the fetched committed base configuration, and dreams
use that same config as today. An unreadable/invalid team ownership configuration
cannot authorize new shared effects or admission through a singleton fallback.
Config transfers require affected factories to quiesce and observe the same
merged setting before resuming; v1 adds no distributed election/lock. With no
legacy setting and no foreign evidence, singleton and an unprepared new team are
indistinguishable; onboarding must satisfy the shared-setting precondition even
in a fresh repo with no backlog. The teammate runs fa init once with their own
GitHub login and supported worker credentials, checks the shared
legacy owner, and starts one gate with independent state. Verify the two gates'
start lists are disjoint using each factory's fa gate status --json
active_runs (or the lane view), foreign stop refuses, foreign work stays visible,
and moved-base merges refresh/refuse. Watch conflict minutes by day on each
factory; the metric is local, not a team aggregate. A non-owner normally skips dreaming; loss of the designated
factory has no automatic failover or remote-offline alarm. Existing local dream
history/logs are the evidence for a person deciding to transfer dream ownership.
If reverting before teammate onboarding, the singleton path remains valid. With
two factories active, stop the joining factory before rolling back ownership
checks. Before a rollback, the owning factory drains or preserves its
runs/WIP/open PRs; a stopped factory's labels alone do not make its work safe for
an older gate. Keep all old gates stopped while foreign work remains actionable.
For an intentional handover, departure, login rename or label correction, affected
factories must have no active worker/dream writer or replayable old writes, retain
WIP and settle open PR responsibility, and agree on the replacement owner. The
authorized collaborator changes the sole by: label (and shared legacy/dream
settings when applicable); refresh identity after an account rename, then resume
only the agreed owning factory. Publication/approval is never an implicit transfer.
Use the issue thread to record the correction; no automatic reassignment, bulk
relabel command, or new coordination service is required. The agent
handles normal conflicts and sees the measured facts; scripts add no judgment.
