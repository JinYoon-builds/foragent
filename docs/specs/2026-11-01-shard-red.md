# Make acceptance shards red after upload, with actionable lost-test logs

A generated foragent-acceptance job is red exactly when its completed shard comparison explicitly reports a nonzero lost passing-test count. Measurement itself succeeds and publishes its report before a final failing verdict step that prints every lost test ID verbatim in its own stdout/stderr. Missing/empty legacy lost output is green. Complete measurement artifacts are readable and comparable regardless of the run conclusion, retaining every existing identity, provenance, freshness, expiry and completeness check. Ordinary CI includes acceptance job failures and their logs, so a red head follows the existing CI repair path and retry budget before queue readiness. A valid red combined report with lost IDs is failed rather than void. Keep the existing merge-turn comparison and trusted-workflow protections. Committed workflow bytes equal public generation. Existing captured test node IDs remain present; changed evidence expectations are rewritten in those same nodes.

One issue, shard-red, lane main, size m, no blockers. The primary producer/generator/comparison files use the implicit main lane; tracker.py is the explicit board-owned transport overlap in .foragent.yml. This remains a draft; source implementation and publication are downstream work.

## Incident and root cause

On 2026-11-01, the supplied incident had 9 of 14 merge-waiting heads with lost passing tests despite green 9/9 PR checks. People judged hand merges on green, and the runs left for repair only at their merge turns. These supplied counts are not newly audited live statistics. Jin chose a truthful shard-job verdict with a missing-output bootstrap exception; this order is not an earlier comparison read in the merge lifecycle.

This is a tool/protocol defect, not an agent judgment problem. ci_shard.main writes comparison=true after measuring both revisions but exports no regression count; the generated workflow ends after artifact upload. GhTracker.pr_acceptance_reports and ci_mode.comparison additionally require run.conclusion == success, so simply making the job red would discard usable evidence and make run_group_ci.check record void. Separately, tracker.pr_checks and pr_failed_logs intentionally filter acceptance jobs/runs out of ordinary CI. A producer-only fix would therefore still hide the red job and its repair logs. Status, evidence and the final verdict have different roles; a completed artifact is not made invalid by the job conclusion.

## Required behavior

- The public comparison step output lost is the decimal cardinality of base.passing_ids minus head.passing_ids for that shard, including explicit 0 for a measured empty loss set. The comparison step still exits successfully and produces comparison=true plus the complete JSON report; the final generated step, after upload, determines regression redness. This small public output name is the order's chosen interface.

- Base failure plus head failure is green, base failure plus head pass is green, and a regressing test in the approved locked-file exclusions is green. Base pass plus head failure is red. Preserve the upload condition independently of lost, artifact name/path, if-no-files-found:error, read-only permissions and fail-fast:false so every shard can finish uploading.

- The final job verdict fails only for an explicitly positive lost count. Absent or empty lost output from the pre-change trusted main tool passes. Do not make the measurement step fail early, hide the verdict with continue-on-error, or couple upload eligibility to the new output. The failing step itself prints every lost full node ID to stdout/stderr, including parameter suffixes, so the existing pr_failed_logs CI repair path supplies those IDs to the worker. Printing only the count or printing IDs only in the successful comparison step is insufficient.

- Read and validate complete measurement artifacts for an exact head when the selected run is completed, whatever its conclusion. Preserve newest-producer selection and pending-run polling; never fall back to an older green run to evade newer evidence. Foreign-run, repository/head identity, workflow/event provenance, expiry, wrong/missing/duplicate shards, scope and completeness refusals remain.

- Acceptance checks and their failure logs participate in the existing ordinary CI status/failure path. A red current head receives the existing retry with its raw regression-step log and the existing budget before any ready row; a repaired fresh head still needs its normal current-base comparison. Use the existing structured CI status and evidence, without classifying log wording or adding an agent reasoning rule.

- run_group_ci judges complete red combined evidence with lost IDs as failed and records its lost reason and evidence metadata. Unusable/incomplete group evidence remains void, even if the run is red. Members retain today's individual fallback, ownership and temporary-resource cleanup. The shared comparison contract should supply this behavior without restructuring group or merge machinery.

- Keep ci_mode.changed_workflows, the current merge-turn comparison, final merge protections and runner_unit_tests trust policy. The existing test_ci_trusted_checks.py controls and exact changed-workflow local-comparison units remain passing. The committed acceptance workflow equals fa ci workflow output under this repository's config.

Its report uploads normally; the final step treats absent/empty lost as green, allowing this PR's CI to bootstrap. The existing changed_workflows check still detects that the PR modifies an acceptance workflow and requires the existing local passing-set comparison before automated merge, even without checks_fallback: local. Do not waive that guard or trust the PR's changed workflow artifacts. After merge, the first eligible issue/group PR execution of the updated workflow that resolves the merged trusted main tool emits lost=0 or a positive count: zero stays green; a positive count fails only after artifact upload. The current workflow is pull_request-triggered, so merging to main does not itself start a push run. Existing completed runs are not retroactively changed.
