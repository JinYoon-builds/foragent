# D82 item 4: the orchestrator calls the architect on evidence

See docs/decisions.md D82 (item 4 rewritten 2026-10-24, addendum, addendum 2). No threshold triggers in code: code shows the numbers, the orchestrator decides.

1. orch-facts: `fa orch facts [--json]`, read-only, from local records only: per-run time split (implementing, checking, test-slot wait, baseline), test-slot queue and waits, hot files (waiting approved issues per declared file, from the overlap data), failure reasons by count, merges since the last tidy. Comparisons: recent-history medians (change detection); waste share per run and overall = time not doing work (slot/baseline waits, repeated work, retries after timeouts) / runtime, an absolute ratio; per resource whether it is idle while work waits (machine, quota expiring unused, test slots, parallelizable work held back by file overlap) and the one binding constraint (quota or machine = normal; a cap, test slots or structure = something to fix). No throughput goal number.
2. orch-architect: `fa orch architect --why "<evidence>"` starts an architect session through the worker session path with the measurement commands and the refactoring procedure (references/refactor.md); its proposals land in the person's decision list, not as orders; the call is recorded (`architect-call`); a second call while one is alive is refused.
Edits: #310 adds the worked example of 2026-10-24 (six runs waited ~1 h for test slots = flow, fixed by the orchestrator; test_runner.py 65 % of unit time = structure, call the architect with that number) and says not to call the architect on a fixed threshold. #157 puts a 'tidy due' request with the evidence into the orchestrator's inbox once per due period instead of deciding itself.
