# Stopping runs safely, and a stop verb for the orchestrator

Evidence (2026-10-24): a review of signal-sending code used a fake identity of 1 and may have killed the user's apps; #197's log showed os.killpg(pid, 0) raising PermissionError after a runner group had exited (the group number belonged to someone else). There was also no way for the orchestrator to stop a running issue and keep its work: runs started on old gate code held slots for 2+ hours.

- #261 (rewritten): stopping a run ends all its descendants, even ones that left its group or session, and ticks reap processes in worktrees of issues that are not running, under kill-safety rules: no killpg by group number after the leader is gone; refuse pid/pgid 1 and the gate's own lineage; touch only processes Foragent started (descendants of recorded runner/executor pids, verified by start time); never match by cwd alone; a PermissionError probe means "not ours". Tests use a fake process table only; real signals and helper processes fail the test.
- orch-stop: `fa orch stop N --keep-work --why "..."` stops a running issue through the scheduler's _kill_run path with #261's rules, keeps the work as the #270 WIP commit, records a stop event, finishes the run as stopped and returns the issue to ready so the next run resumes on current code; it refuses when N is not running, without --why, or when the recorded pid fails the safety rules.
