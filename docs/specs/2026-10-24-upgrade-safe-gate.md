# Gate state survives upgrades, and a crashing tick is noticed

Evidence (2026-10-24 ~21:50-22:30 KST): after #261's reinstall added `process_identities` to the persisted Run record, five runners started on the previous code died in StateStore.get_run with TypeError (unexpected keyword argument). Every tick then crashed in scheduler_recovery for about 40 minutes (launchd kept restarting it); nothing noticed because the stall detector and crash recovery run inside the crashing tick. The orchestrator found it by chance and finished the dead runs by hand (pid verified gone, no signal). The refused-stop crash itself is fixed outside (gate broken).

- state-records-tolerant (first): every persisted state record loads through one tolerant loader `foragent.records.load_record(cls, data)`: unknown fields are ignored and kept on write-back, missing fields get defaults; an AST guard covers every dataclass mapping load site except Config, which stays strict (unknown .foragent.yml keys still raise).
- tick-failure-alert (next): each `fa gate tick` writes tick-outcome.json (time, ok/failed, error type, short message, log path, consecutive failures) even when it raises; after `tick_failure_alert` (default 3) consecutive failures one orchestrator inbox request and one push are created; the next success resolves that request without a new push; `fa gate status --json` exposes tick_outcome.
