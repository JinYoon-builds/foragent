# Ideas parking lot

Ideas Jin wants to keep but not order yet. An idea moves to `decisions.md` when Jin decides it, and to an order after that. Newest first.

## 2026-10-24

- **README and launch: engine first, squirrels second.** Many agent-visualization projects put characters on agents (offices, Minecraft-like worlds); Foragent must not look like one. Lead with measured engine claims (no broken merges overnight, merges per day before/after, an OS for agents, the highway metaphor), then show the squirrel view as the memorable face. Keep the D64 rule that every squirrel pose means a real state (working, waiting, blocked, your turn), keep a plain table view for serious users, and put information (orchestrator panel #172, progress in words #169) above decoration. Lead with outcomes, not counts ("150 skills" style is the opposite of D58 addendum 4). Repository went public 2026-10-24 (CI billing); README and decisions.md wording to review before any launch.

- **Several projects on one machine.** Jin expects to run about four projects at once. The machine-wide budgets (#106 parallel, #243 test slots) already stop projects from thrashing the machine together, but: each project has fixed memory (orchestrator, lane view, interviewer; roughly 0.5-1 GB per project), and when slots are short nobody decides which project gets them (first come today; the D80 plan orders work only inside one project). Needed later: a machine-level priority across projects that Jin sets ("project A first this week"), the facts dashboard (#333) across projects, and heavier offload of acceptance checks to GitHub Actions for public repos. Size the next machine from measurements once the bottlenecks are cleared.

- **One merge path (retire premerge as a separate command).** The regression check on the merged result is always needed (industry: merge queues — GitHub Merge Queue, GitLab merge trains, Bors, Zuul). But today it exists twice: inside the runner (gate merges) and in `fa orch premerge` (human or outside merges), and the copies drift (premerge missed test slots, #331). Let people only approve ("merge when ready") and let the runner do every merge, like GitHub Merge Queue; then one check, no premerge command. After #331.

- **Smaller squirrel pixels.** Jin finds the pixels large. Quadrant (2x2) and sextant (2x3) glyphs were previewed on 2026-10-24 and break the art (two colours per cell smear outlines and eyes), so keep half blocks. If size still matters, redraw smaller sprites in the same half-block style (e.g. orchestrator 18x15 to about 12x10) in a design session with 2-3 drafts side by side (D72).

- **Architect squirrel in the lane view (D82).** Appears only while the architect is called, with one line on what it examines ("runner.py: 7 issues waiting — reviewing structure"), leaves its result (e.g. "2 tidy orders proposed") in Jin's decision list, then disappears. Normally only a status-line count ("next tidy in 12 merges"). Visually distinct from the big orchestrator squirrel (#311), e.g. glasses or a blueprint; the look is Jin's call. After #157.

- **Write up how Foragent evolved.** Sources: `decisions.md` (D1-D81, each with date and reason), git history, research notes, scorecard numbers. Candidate threads: deterministic gate vs judging orchestrator (and why D80 came back to Jin's first instinct); building Foragent with Foragent; wrong diagnoses and what measurement fixed them (machine contention, GitHub limits, test counts); incidents and the safety lines they produced (the kill incident, unchecked outside merges); speed work as plumbing, not smarter models. Central claim (Jin, 2026-10-24): the model sets how good each worker is; the structure sets how many workers can be useful at once — Brooks's law still holds for agents. Metaphor: Foragent does not build a smarter car, it builds the highway so several supercars can run at full speed instead of crawling on a country road (lanes = lanes, code structure = lane width, gate/orchestrator = traffic control, AIMD = road capacity, D81 = lighter loads, WIP preservation = repair stops). Claim speed-ups only with the throughput baseline/after numbers.

- **Ask for a star once, after real value.** When Foragent has merged, say, 10 issues, show one line in a human-facing screen (interview or status report, never gate logs): "Foragent merged 10 issues. Star the repo? (yes / no, never ask again)". Only on an explicit yes does the agent star via `gh`; never star silently or offer rewards for stars (trust, and GitHub's rules on inflating stars). Ask once only.

- **`fa` checks for updates (needed before the open-source release).** Users install with `uv tool install` and never learn about new versions. On `/fa` or `fa`, check the latest release once a day and offer a one-line update. After updating, restart the gate between ticks and let running runners finish on the old code; the self-merge reinstall (`orch_reinstall.after_merge`) already does this and can be reused.

- **Docs that explain Foragent through operating-system concepts (for the open-source release).** One page per element, mapped to the OS idea it mirrors: policy vs mechanism (orchestrator plan vs gate, D80), the scheduler and run queues (lanes, including the priority inversion behind #138), AIMD parallelism as TCP congestion control (#106), test slots as semaphores (#243), lanes as mutual exclusion by file ownership, plan expiry as a lease, crash/stall recovery as process supervision. Each page also says where the analogy breaks: the "processes" judge and can be wrong, and the scarce resources are token quotas and API limits rather than CPU. IPC map: planning ↔ orchestrator messages are literally Unix domain sockets; the orchestrator request box is a message queue; shared state files (issue snapshot, runs, test slots) with flock are shared memory with a mutex; the GitHub outbox (#241) is a write-back queue; gate kicks are wake-up signals; heartbeats (#127) are a watchdog; orch-events.jsonl is an append-only event log; runner output to log files is a pipe. Scheduling: issues are non-preemptive jobs with an expensive context switch (worker conversation, worktree, phase), so the convoy effect and late-arriving urgent work are real (#138's 8-hour queue; #235 waiting for a slot); costly preemption exists as WIP commit (#270) + session resume (#236) + fa orch stop (#370). Runtime is unknown like in MLFQ: size labels are guesses, the 90-minute budget is the time slice, and failure feedback raises the model tier (the opposite of MLFQ demotion: harder work gets a stronger worker). Ideas to borrow as orchestrator judgement, not gate rules: shortest-expected first from scorecard history, split issues that keep using the whole slice, aging so old issues are not starved. Concurrency cases from 2026-10-24: changed files diffed against the moving main let other merges leak in (#344, #151) — an isolation failure fixed like snapshot isolation (diff from the merge base); a tick acting on a minutes-old issue list recovered runs that had just finished (#295) — TOCTOU fixed by re-reading right before acting; test slots as semaphores starved by work outside them (premerge, #331). Back the claims with scorecard numbers (merges per hour, regressions caught). Write after the core is stable.

## 2026-10-23

- **Lane workers using the harness's own multi-agent features.** A Claude worker could fan out subagents inside its run (investigate, implement, test in parallel) and use the idle Claude quota. Risks seen the same day: more processes and machine contention, orphaned background shells (#184), subagents editing the same worktree at once (the conflict lanes exist to prevent), and runs the gate and scorecard cannot see. Revisit after #106 (machine budget), #243 (test slots) and #261 (orphan cleanup). Open read-only helpers (investigation, review) first, for large issues only.
- **Heavy checks on GitHub Actions for public repositories.** Actions minutes are free for public repos and can shard the suite across runners. Keep the local machine as the default (users' repos may be private and have limited minutes); offer Actions as an opt-in, and avoid polling GitHub for results (the API limit). Do after reducing repeated test runs (#272, #257, #243).
- **A local-model worker.** When local models are good enough, easy issues could go to a local model for free and hard ones to Claude or Codex; one more choice for D74's executor selection.
- **Faster unit tests.** Many tests build a temporary git repository and run programs, about 0.2-0.7 s each. Reusing fixtures could make the suite several times faster (a D68 tidy task).
- **Narrower related-test selection.** Changing a central module selects about 1,900 tests. Coverage-based selection would cut this but can miss breakages; a trade-off for Jin after the scorecard (D77) shows check-phase time.
- **Time budget by issue size.** Every run gets 90 minutes; large issues could get more. Decide from the scorecard's per-size times.
