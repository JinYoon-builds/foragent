# foragent는 무엇이 다른가

사람들이 가장 먼저 묻는 질문은 두 가지예요. "그냥 goal 기능 아니야?"와 "그냥 훅 만든 거 아니야?"예요. 이 문서는 두 질문에 답해요. 그리고 비슷한 오픈소스와 foragent를 나란히 놓고 비교해요.

## 한 문장으로

foragent는 에이전트 한 세션의 도구들(오케스트레이터, 서브에이전트, goal, 훅)을 프로젝트 전체와 긴 시간 단위로 넓혀요. 몇 시간이 아니라 며칠, 몇 주 단위예요. 그 사이를 코드(게이트)가 이어 줘요.

## goal과 비교

goal은 에이전트 하나에게 목표 하나를 줘요. 에이전트는 스스로 다 됐다고 판단할 때까지 계속 일해요.

| | goal | foragent |
|---|---|---|
| 일하는 단위 | 에이전트 하나, 세션 하나 | 레인 여러 개가 동시에 |
| "다 됐다" 판단 | 에이전트 스스로 | 승인할 때 잠근 인수 시험과 독립 리뷰가 판단해요. 에이전트는 그 시험을 고칠 수 없어요 |
| 세션이 끝나면 | 목표도 같이 끝나요 | 게이트가 저장된 브랜치에서 이어서 다시 시켜요 |
| 일감 | 사람이 목표를 하나씩 줘요 | 레인이 승인된 이슈를 스스로 가져와요 |
| 다른 작업과의 충돌 | 신경 쓰지 않아요 | 미리 선언한 파일과 실제로 고친 파일로 누가 기다릴지 정해요(파일마다 동시에 고칠 수 있는 수에 한도가 있어요). 머지할 때마다 최신 main 위에서 다시 확인해요 |
| 머지 | 사람이 해요 | 검증을 통과한 작업이 짧은 머지 잠금 안에서 스스로 머지돼요(여러 개를 묶어 머지하는 기능은 #459 이후) |

goal은 에이전트를 믿고 맡기는 방식이에요. foragent는 에이전트를 믿지 않아도 되게 만든 방식이에요. 그래도 goal은 foragent 안에서 쓸모가 있어요. 레인 하나가 이슈 하나를 끝낼 때 쓰기 좋아요.

## 훅과 비교

훅은 에이전트 세션 안에서, 에이전트가 무언가를 할 때 돌아요. 예를 들면 도구를 쓰기 직전이나 일을 끝내려 할 때예요.

| | 훅 | 게이트 |
|---|---|---|
| 어디서 도나 | 에이전트 세션 하나 안에서 | 모든 세션 밖에서, 독립 프로그램으로 |
| 언제 도나 | 에이전트가 행동할 때만 | 정해진 간격으로, 에이전트가 없어도 |
| 성격 | 반응형: 행동을 확인하거나 막아요 | 능동형: 일을 시작하고, 레인을 배정하고, 멈춘 실행을 살리고, 머지하고, 오케스트레이터를 깨워요 |
| 범위 | 세션 하나 | 저장소의 모든 레인 |
| 세션이 죽으면 | 같이 죽어요 | 그대로 돌아요 |

둘은 함께 써요. 게이트가 레인 세션 안에 훅을 심어요. 예를 들어 `fa gate check-done`은 에이전트가 멈추려 할 때 인수 시험을 돌려요. 통과할 때까지 에이전트가 일을 계속하게 해요.

## 오케스트레이터 + 서브에이전트 + goal과 비교

세션 하나 안에서도 foragent의 일부를 다시 만들 수 있어요. 오케스트레이터 에이전트가 이슈를 서브에이전트에게 나눠 주고, 서브에이전트마다 goal을 돌리면 돼요. 그런데 이 방식에는 다음이 빠져요.

- **이어지기:** 오케스트레이터 세션이 끝나거나 한도에 걸리면 모두 멈춰요. foragent는 상태를 파일에 남기고, 게이트가 계속 돌아요.
- **에이전트가 바꿀 수 없는 완료 기준:** foragent는 승인할 때 인수 시험을 잠가요.
- **머지 전 재검증:** foragent는 머지하기 전에 최신 main 위에서 짧은 머지 잠금 안에서 다시 확인해요.
- **기계에 맞춘 동시 실행 수:** 동시에 도는 실행 수가 CPU 부하를 따라가요. 메모리가 위험 수준이면 새 실행을 멈춰요.
- **끊긴 작업 지키기:** 멈춘 작업을 커밋해 두고 이어서 해요. 동시에 도는 정리 작업이 그 작업을 지우지 못해요.
- **가벼운 오케스트레이터:** 결과가 오케스트레이터의 대화에 쌓이지 않아요. 오케스트레이터는 사실을 읽고 판단만 해요.

## 레인

레인은 프로젝트의 한 영역을 맡은 에이전트예요.

- `fa init`이 레인을 만들고, 레인마다 스킬을 달아 줘요.
- 레인은 자기 일감(이슈)을 스스로 가져와요.
- 레인마다 기억이 따로 있어요. 그래서 쓸수록 자기 영역을 배워요.

git 워크트리로 작업 공간을 나누는 건 이 분야의 기본이에요. foragent가 그 위에 더하는 것은 세 가지예요. 영역을 맡는 레인, 배우는 레인, 기계 부하를 따라 늘고 주는 동시 실행 수예요.

## 비슷한 오픈소스와 비교 (2026-10-26 조사)

| 계층 | 예 | 기본으로 사람 없이 머지하나 |
|---|---|---|
| 회사 단위 관리 | Paperclip | 아니요. 완료는 설정한 리뷰나 승인 단계가 정해요 |
| 조율과 검증 | Gas Town, OpenAI Symphony, Orchestrator.inc, foragent | Gas Town은 예(이분 탐색 머지 큐). Symphony는 "Human Review"에서 멈춰요. Orchestrator.inc는 "머지 준비 완료"에서 멈춰요 |
| 병렬 실행 도구 | Claude Squad, Vibe Kanban, Orca, Conductor | 아니요. 사람이 변경 내용을 보고 머지해요 |
| 단일 에이전트 | Claude Code, Codex CLI, OpenCode, Goose, 가재코드 | 아니요. 세션 하나에 작업 하나예요 |

조사한 프로젝트 가운데 아래 네 가지를 함께 갖춘 곳은 없었어요.

1. 승인할 때 잠그는 인수 시험
2. 머지 전에 최신 main 위에서 다시 확인
3. 영역을 맡고 배우는 레인
4. GitHub 이슈, 프로젝트 보드, PR만으로 돌아가는 흐름

다만 각 프로젝트의 README와 공개 문서만 보고 판단했어요. 코드를 읽지는 않았어요.

## "사람 없이 머지"를 간판으로 삼지 않는 이유

사람 없이 머지한다고 하면 위험하게 들려요. 대부분의 팀은 일부러 사람이 머지 버튼을 눌러요. foragent는 사람을 없애는 게 아니라, 사람이 보는 위치를 옮겨요.

- **일을 시작하기 전:** 사람은 이슈의 목표와 인수 시험, 곧 의도를 리뷰해요.
- **결과가 들어간 뒤:** 사람은 결과를 직접 써 봐요.
- **그 사이:** 잠긴 시험이 지켜요.

중요한 경로는 사람이 머지하도록 정할 수도 있어요. `.foragent.yml`의 `always_human`에 넣거나 위험 지도에서 `always_human`으로 표시하면 그 경로의 머지는 사람이 정해요.
