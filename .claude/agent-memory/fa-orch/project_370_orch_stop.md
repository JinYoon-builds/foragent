- `orch.stop()` holds `store.hold_tick_lock()` (polling up to `STOP_LOCK_WAIT_S`) through the precheck, kill and label changes, then kicks a tick after releasing the lock. Otherwise the dying runner's own kicked tick sees a finished run that still has `running`, treats it as an orphan (crashed) and can relaunch it. Success means the run record finished as `stopped`, not that `_kill_run` returned True. It builds a `scheduler.TickContext` from the RunContext (default `kill_runner=kill_process_group`). It first records `update_run(outcome="stopped", detail="stopped: <why>")` and then calls `scheduler._kill_run(..., outcome="stopped")`. If the kill does not end the run as stopped, it restores the previous outcome/detail.
- **Why record first:** a real runner that gets SIGTERM saves its own WIP (`_execute` finally uses `run.outcome or outcome`) and removes the worktree before `_kill_run` can. Its `run_issue` SystemExit handler also adds `blocked`, unless the recorded outcome is `stalled-restart` or `stopped`. `review_only` has its own SystemExit path, and it honors `stopped` too: no blocked flag, no label change. A caller-only reason parameter on `_kill_run` misses this (review of 2026-10-26).
- `_preserve_failed_implementation` swaps reason `stopped` for `run.detail`, so every saver names the why. `STOPPED` lives in `run_publish.py`.
- Unsafe recorded PIDs are refused with **no** state change, because `_stop_run_processes` writes a `stop-refused` flag. `scheduler_stop.stop_target_refusal(run)` checks first and only reads `processes.list_processes()` and `_protected()`. It also refuses PIDs in `ProcessTable.unreadable`; turning the table into a dict drops those PIDs.
- `--keep-work`/`--why` are argparse-required. Verb wiring lives in `src/foragent/commands/orch.py` (main split `cli.py` into `commands/<group>.py`; on a `cli.py` conflict, take main's file and move the verb).
- Tests: acceptance `test_orch_stop.py` + `test_keep_unfinished_work.py`; boundary `tests/test_orch_stop_unit.py`, `tests/test_runner.py::test_runner_stop_leaves_orchestrator_stop_labels_and_reason_to_the_verb` (the run_case teardown requires `running` removed).
- Review round 4 (defect class "never report success after losing work"): a failed WIP save keeps the worktree. `run_publish.keep_unsaved_work()` logs, records a `wip-preservation-failed` event, sets the run outcome to `wip-not-saved` and flags `retries-exceeded`. `_remove_run_worktree` returns False when the save fails. `_kill_run` then finishes the run as `wip-not-saved` and returns False, so stall restart and timeout flag do not apply. `_finish_dead_run` and `_recover_orphan` skip crash/stall recovery. On the runner side, the `_implement_and_publish` finally raises `WipNotSaved`, and `run_issue` skips its worktree removal. A failed push counts as a failed save even when a local commit exists.
- `.foragent/acceptance-exclusions.json` is written by the CI-mode runner (order edits to acceptance files during a run add entries). Never edit it by hand; rebut reviewer points about it. Since 502b4c8 (2026-10-26) main no longer tracks it and lists it in `.gitignore`; resolve a modify/delete conflict by deleting the working-tree copy.
- Review round 5: every caller of `_implement_and_publish` must keep the worktree on `WipNotSaved`: `run_issue` (via `_execute`) and `review_only`'s inline CI repair (`kept` flag skips its finally removal). If the issue has an open PR, stop flags `retries-exceeded` ("Stopped with open PR #N; rerun review or retry implementation.") instead of `ready`, because a tick clears `ready` while a PR is open. This matches the crash and stall precedent.
- Baseline comparison pitfall (2026-10-26): after a runner merge, HEAD is a merge whose first parent is this issue's own WIP. `HEAD^` therefore already contains the change. Take main as the second parent (`git rev-list --parents -1 HEAD`) and check `hasattr(foragent.orch, "stop")` is False before trusting a base run. The `test_run_publish.py` parallel tests (`Event.wait(10)`) fail on main too when load average is ~17.
- Defect-class sweep (2026-10-26 retry):
  - (a) Missing evidence treated as safe: besides unreadable PIDs, `stop_target_refusal` also refuses `run.pid is None` and a runner PID that is not in `process_identities`. The existing checks run first, so their messages stay the same.
  - (b) A destination state the next tick undoes or contradicts: besides an open PR, `orch.stop` does not add `ready` to a closed issue or one held by `blocked`/`needs-human`. It only removes `running`, as in `_restore_after_crash`; the hold check runs before the PR check.
